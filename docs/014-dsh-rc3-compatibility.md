# 014 DSH 0.2.2 rc.3 compatibility candidate

This is a development candidate, not a production deployment or a claim of complete compatibility. The project's development dependencies are pinned to rc.3, while its existing peer and engine ranges still admit rc.1 and later prereleases within the range. A version range is not a runtime safety guarantee.

The [rc.3 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-rc.3) describe an optional chat-import plugin and a Windows Desktop updater fix. The installed upgrade index does not contain an rc.2-to-rc.3 guide; that absence does not prove the interfaces used by this project are unchanged. The earlier [rc.2 investigation](013-dsh-rc2-subagent-lifecycle.md) describes the ownership and admission changes relevant to this candidate.

The candidate's worker preset no longer provides native subagent tools. A project guard rejects known native subagent tools for recognized managed workers and their subagents, including workers retaining an older preset. It follows available live and persisted ancestry for up to 128 levels and two seconds, but missing, unreadable, cyclic, timed-out or deeper ancestry remains unrecognized. It cannot revoke already prepared calls or cover other entry points or external or GUI work. It is not complete isolation.

The independently locked [rc.3 subagent contracts](../contracts/subagent/rc3/contract.test.mjs) exercise the real rc.3 subagent runtime with in-memory substitutes. On rc.2/rc.3, stopping best-effort interrupts catalogued children and waits for tree work, rather than releasing local activations. A caller-delivered external execution is not interrupted, external disposal failure can be missed, and a local child and its unclaimed inbox can remain parked. The candidate reports cleanup unconfirmed if the catalog contains any child or diagnostic, including historical entries, or tree work was observed, even without another error. An empty catalog or a wait returning false does not prove no residual activity. The existing persistent Ticket fence blocks later automated work and is not automatically released; investigate the original process and residual work. Crashes before intent recording, direct GUI actions, catalog gaps and unconfirmed external work remain outside that safeguard. The rc.1 path instead releases live catalogued children. `drainDescendants` is not a drop-in replacement: it closes admission for the reusable root until that root leaves the registry. On in-process shutdown failure the candidate retains the database and state lock; this is not evidence of production deployment.

On Windows with Node.js 24.21.0, the candidate passed type checking, build, 1,451 default tests (34 skipped) and 13 separately locked rc.1/rc.2/rc.3 subagent contracts. Earlier validation reproduced four worker-shutdown test failures on both rc.1 and rc.3: those tests called the report tool directly without ending the simulated worker turn. The fixtures now explicitly end that turn and wait for its stop marker. This fixes the test setup, not evidence about real process cleanup.

The contracts do not test a real external process, full DSH profile, model, cross-process recovery or production deployment. Validate changes with an independently configured non-production profile, DSH home, state, port, credentials and test repository, with Feishu disabled; a worktree alone does not isolate these resources. Do not upgrade or restart production based on this candidate alone.
