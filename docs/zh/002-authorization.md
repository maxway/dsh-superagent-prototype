# 002 授权机制

[English](../002-authorization.md) | **简体中文**

授权机制（Authorization）决定谁可以开始工作，以及该工作可以包含什么。本文建立在 [001 领域模型](001-domain.md) 之上。

宿主执行允许名单、规则和授权（Mandate）。消息、评论和被引用的文档都是决定的输入；它们不能改变这些权限。

## 触发的两条路径

### 评估：决定是否开始工作

来源会记录一条消息是否面向智能体：`mention` 表示提及机器人或智能体账号，`direct` 表示私信。准入检查发送者和来源的策略：

- 允许名单上的人向智能体发消息，构成明确请求。
- 人在已有工单的线程上的跟进，遵循下面的规则。
- 其他人发出的消息按其接收范围套用准入表。
- 来源机器人列表上的机器人可以产生推断的候选，永不会产生明确请求。其他机器人不予准入。

### 订阅：继续已有的工作

已订阅线程上的每条消息都会作为上下文到达订阅了它的工单，包括来自机器人和 CI 的消息。这种投递绕开准入，不授予新的权限。每个工单仍受其授权的限制。

人在工单自己的线程上发的消息，由该工单的执行器决定如何处理。主 Session 把一条消息附加到工单时也一样。执行器拥有该消息期间，它不经过评估，也不会得到决定。每个执行器要么在其工单的范围内处理请求，要么把它交回，以便路由到别处。

只要工单是活动的，所有权就继续，即使人移除了它的订阅。所有权也覆盖已结束的工单，前提是该工单不是被人停止的，并且有消息在等待使其恢复。

主 Session 会收到一条跟进通知。执行器拥有该消息期间，主 Session 只能按人的请求停止工作；接单、附加、忽略和重新排队都会被拒绝。停止仍会带着下文所述的跟进强度通过准入。

### 交回与释放跟进

当一条消息请求超出工单范围的工作，或属于另一个工单时，执行器会把它交回一次。工单保留其订阅。如果附加的线程无关，执行器会把它在那里拥有的消息交回。

只有当没有任何工单仍拥有某条消息时，它才会进入一次新的评估。其候选会包含各执行器给出的原因。准入把它当作该线程上的普通消息来判断，主 Session 可以接单、把它附加到别处或忽略它。交回一条工单并不拥有的消息，例如机器人消息或人已经送入评估的消息，不会排队任何内容。

工单结束时，会释放其执行器未读取或未接手的跟进。这些包括从未投递给执行器的消息，以及在其最后一次报告或回合结束之后投递的消息，前提是执行器既未确认、未回复，也未交回它们。每条被释放的消息在没有其他工单拥有它时进入评估。停止只结束被停止工单的工作。

被停止的工单不会把它的停止消息再次送入评估，除非另一个工单把它交回。停止它的主 Session 可以把消息的其余部分作为新工作接单。

人可以从面板把一条有归属的跟进送入评估。如果主 Session 随后把它重新附加到一个活动工单，执行器会再次收到它。当没有任何有效的判断覆盖该消息时，面板也会提供重新评估。

### 仅作上下文的订阅

执行器可以为获取上下文而关注一个相关线程，例如另一个 Issue 或 pull request。该线程的消息会到达工单，但不授予权限或跟进强度。那里的人的消息不会使已结束的工单恢复，除非主 Session 从该线程附加一条消息。主 Session 关于其他工作的说明也只是上下文。

没有到达任何工单的人的消息，包括其工单已被人停止的线程上的消息，走评估路径。机器人消息无论是否投递到已订阅的工单，都走该路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit | 名单上的人向智能体发消息，或在已有工单的线程上跟进；准入表中设为明确请求的单元格 |
| inferred | 不在名单上的人在已有工单的线程上跟进，除非其在准入表中的单元格为明确；准入表中设为推断候选的单元格；来源机器人列表上的机器人所发的消息，且该消息面向智能体，或到达来源能接收每条消息的位置 |
| not admitted | 任何其他机器人的消息、准入表忽略的一切，以及接单模式为 `off` 时的每个推断情形 |

对不在名单上的人，明确的准入单元格即使在线程已有工单时也优先，并且在每种接单模式下都有效。否则其跟进属于推断，在 `off` 模式下不予准入。仅在为获取上下文而关注的线程上，消息使用准入表，而不是跟进强度。

## 准入

每个来源的策略都有一张准入表。它的行是接收范围：

- **飞书：** 每个已配置的群、机器人从中收到提及的其他群，以及私信。只有在飞书卡片上将 **其他群** 设为 **仅 @** 时，才会接收其他群。
- **GitHub：** 新 Issue、新 pull request、评论和默认分支的 CI。
- **GitLab：** 新 Issue、合并请求、note 和 CI。

一行最多有三个单元格。每个单元格决定一条消息会变成明确请求、推断候选，还是什么都不是：

| 单元格 | 取值 | 默认值 |
| --- | --- | --- |
| 在名单上，未面向智能体 | inferred、ignore | inferred |
| 不在名单上，面向智能体 | explicit、inferred、ignore | ignore |
| 不在名单上，未面向智能体 | inferred、ignore | ignore |

针对未面向智能体的消息的单元格，只在来源能接收每条消息的地方可用，例如设为 **全部消息** 的飞书群，或开启了接收全部开关的 GitHub 或 GitLab 范围。CI 结果没有发送者，因此其所在行只提供最后一个单元格。机器人消息使用机器人列表，而不是这些单元格。

把「不在名单上但面向智能体」的单元格设为 explicit，可以让该范围内的任何人通过提及智能体来请求工作。这对专门的支持群可能有用。推断候选仍取决于接单模式。跟进通常绕过此表，但明确的单元格仍会授予明确强度。

准入表是策略版本的一部分。削弱某个单元格不会立即停止在其下接单的开放工单。当这些工单在恢复前重新校验时，这可能撤销它们的授权。

### 机器人与自动评审者

宿主把 GitHub Apps、以 `[bot]` 结尾的登录名、GitLab 机器人用户和飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 的机器人，其消息可以成为推断候选。它们必须面向智能体，或发布在能接收每条消息的范围内。它们不能发出明确请求，也不能停止工单。

使用普通账号的自动评审者，在宿主看来算作人。它的评论会到达已订阅的工单并产生跟进通知。团队提示词文本必须把这类账号标识为自动评审者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确的候选。一次调用可以包含多个接单、附加、停止或忽略决定。每一项都独立处理：某一项被拒绝或缺少字段，不会阻止其他项执行。

推断候选通常需要完整的研判。有一个捷径：如果它的卡片明显不涉及任何已启用的规则，例如普通聊天或无关讨论，主 Session 可以直接忽略它。决定会记录 `ignoredFromCard`，以便与规则研判区分。主 Session 在其策略提示词段落中读取已启用的规则。

接受推断候选始终需要研判。直接接单会拒绝准入未以明确强度接纳的触发。

## 接单模式与规则

接单模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断的内容都不会成为候选，例如未面向智能体的消息、机器人的消息，或不在名单上的人的跟进 |
| `observe`（默认） | 对推断候选进行研判；肯定的研判记录为带「would accept」标记的忽略，不会接受任何内容 |
| `auto` | 对推断候选的肯定研判会接受它 |

明确请求在每种模式下都有效。从 `observe` 开始，在查看记录的决定后切换到 `auto`。每次研判都会对每条已启用的规则恰好判断一次，无论是否匹配。主动接单要求至少匹配一条规则。

每条规则描述一种主动工作。工单的授权会记录匹配的规则，其执行器会收到规则的名称和说明。

对该工单而言，规则中的过程和沟通要求会覆盖默认值。静默规则可以抑制确认；评审规则可以指定合并前所需的评审者和批准。适用于每个工单的要求则应放在团队提示词段落中。

## 策略版本

规则、接单模式和每个来源的策略共同构成策略版本。每个授权都会记录它是在哪个版本下接单的。

版本变更会丢弃正在运行的评估，并重新排队它们的触发。它还会向每个受影响的活动工单发送一条策略变更输入。该输入会说明属于以下哪种情况：

- 某条匹配的规则发生了变化，包括其新文本，或不再适用；
- 请求者可能不再能开始工作；或
- 主动工作不再被接受，例如因为模式已从 `auto` 变更。

未受影响的工单不会收到通知。该变更不会立即撤销活动工单的授权。

来源配置与策略分开。它控制系统接收什么：读取哪些群，以及某个范围接收全部消息还是仅接收提及。授权会记录其来源和接收范围。恢复需要来源仍在监听该线程，但不要求它仍能接收那里的每条消息。

来源关闭期间，回复会等待。如果来源不再监听其目的地，回复会被丢弃。

对执行器可以用自己的结果做什么的限制，例如何时可以合并，并不决定谁可以授权工作。它属于智能体的指令，而不属于策略。

## 恢复与停止

已结束的工单保留其授权。人在其某个自有线程上的消息可以恢复同一工作，无需新的评估或决定，无论发送者是谁。机器人和 CI 不会唤醒已结束的工单。执行器决定请求是否符合范围，如果不符合，就结束这一回合。

只有三种操作会改变授权：接单创建它、人的停止撤回它、重新校验失败撤销它。被人停止的工单保持已结束，不再接收任何内容。在那里请求的工作需要新的接单。

### 恢复前的重新校验

来源必须仍在监听原来的线程。其余检查取决于授权的依据：

- 明确的跟进授权可以通过。
- 推断的授权需要 `auto` 模式，且其匹配的规则仍已启用。
- 由表格单元格准入的授权，在当前的表格和发送者成员关系下，必须仍能获得至少其原始强度。因此，把发送者从名单中移除，可能撤销通过「名单上发送者」单元格接单的授权。
- 机器人的授权要求该机器人仍在来源的机器人列表上。推断的表格授权和机器人授权还需要 `auto` 模式以及已启用的匹配规则。
- 其他授权要求发送者仍在来源的允许名单上。

如果重新校验失败，工单保持已结束，不接收任何等待中的消息。每条消息都被视为没有到达任何工单；如果没有其他工单拥有它，它进入评估。主 Session 不会被告知它到达了某个执行器（worker）。这也适用于暂停处理之后。附加到该工单会被拒绝，后续工作需要新的接单。

- **人在线程中说「stop」是一个普通的触发，** 由评估决定停止。执行器不能宣称有人要求它停止。
- **面板中的停止是一条命令。** 它直接作用于工单，并记录为手动停止。
- **等待条件属于来源。** 诸如「N 小时内没有负责人」的条件会是一个来源，它自己等待并再次检查；评估从不等待。

## 评估未完成时

时限从候选到达主 Session 时开始。等待投递的时间不计入，未投递的候选永远不会过期。

超时的评估会重新排队其触发，以便再试一次。连续两次重试之后，第三次超时会记录 `unavailable`。研判失败也会记录 `unavailable`；之后的一个触发可以启动新的评估。策略变更或依据过时策略作出的决定会记录 `unavailable`，并立即在当前版本下重新排队该批次。

`evals` 健康条目会报告最近一小时内未解决的 unavailable 决定。`scripts/dsh-superagent status` 会包含该错误。

只有当 unavailable 决定不到 24 小时、仍是其线程上最新的决定、尚未被忽略，并且该线程既未排队也不在评估时，面板才会请求人工关注。人可以再次评估该触发，或忽略该问题。
