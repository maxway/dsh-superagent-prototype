# 012 同一会话中的 worker 交接设计

状态：**更广泛的方案，尚未实现**。本文提出保留完整可用上下文、保证单一有效接收者的通用飞书 Thread 交接。[执行流程](003-execution.md#能力档位与模型)中范围较窄的 low→high 能力接力，针对同一任务继承原授权，使用 worker 摘要，并允许切换期间偶发重复；它没有实现本文拟议的协议和保证。本文方案及该较窄实现均不授权直接部署。

## 当前行为与问题

- [领域模型](001-domain.md)将 Subscription 定义为 Thread 与 Ticket 的多对多关系；多个独立工作可订阅同一 Thread。新 Trigger 向所有符合条件的订阅者扇出，非人工停止的已结束 Ticket 也可能被人的消息恢复。worker 越权请求 handback 只释放该消息，不移除订阅。
- [执行流程](003-execution.md)中每个 Ticket 有自己的 Session、目录、Assignment、报告和 Inputs；重试 Assignment 并不是更换 Ticket。Ticket 的 Mandate 和适用策略决定其范围，不能通过复制上下文扩展授权。历史上记录为 `query` 或 `research` 的 Ticket 保留只读限制。
- 飞书接入只能使用实际收到的事件，不能事后读取聊天历史或下载图片。Thread 记录不是完整群聊记录；模型看到的摘要也不是完整原文。缺失消息不能靠交接补回。
- 因此旧 Ticket 结束或简单取消订阅并不足以构成交接：已有消息的归属、待发送回复、运行中的工作和新 Ticket 的上下文都可能留在旧侧。现有设计的多订阅适合同一 Thread 中确实存在多个独立工作，但不满足本场景的单一接收者要求。

## 边界与不变量

本方案的「会话」指 Source 定义的 **Feishu Thread key**，不是整个群聊、所有话题或跨 Source 的关联 Thread。第一版只对显式切换的 Thread 启用单接收者；其他 Thread、Git 评审线程和普通 context-only 订阅保留原有多对多语义。不同话题是否也需要一个群级接收者是另一个产品决定。

1. 一个已启用交接的 Thread，任意提交时刻最多一个有效接收 Ticket；切换期间可以暂时没有接收者，但 Trigger 必须持久排队。旧 Ticket 不再从任何来源接收新 Input 或被唤醒；关闭它的所有订阅，而不是仅移除当前 Thread。旧 Ticket 的历史、Mandate、报告和已发布产物保留审计，不把交接伪装成人工 stop。
2. 用新的接单 Decision 和 Mandate 授权新 Ticket；旧聊天、旧 Mandate 和交接摘要只提供上下文，不授予执行权限。新请求、强度、策略与发起人依现行准入判断；未获授权不创建或启动新 worker。旧 Ticket 若被明确停止或有等待确认的人工 hold，交接不能绕过该限制。
3. 保证的是每个已接收 Trigger 的**唯一归属和幂等投递**，不是外部系统的恰好一次副作用。发送到飞书、Git 服务或执行中的命令无法通过数据库事务撤销；不确定结果需核实，不得盲目重做。
4. 「完整上下文」指本系统在切换水位之前持久保存且允许新 Ticket 读取的原始会话记录，包含接收的消息及可用的发送结果；不声称包含未收到、已删除、无权限访问或本来不可用的内容。摘要只作索引，不替代原文；记录权限和保留策略必须适用。

## 发起和准备

切换可由旧 worker 对超出当前 Ticket 授权范围的请求 handback 后，由路由器判断，或由人明确要求；普通后续消息、bot/CI、单纯的任务结束均不自动切换。handoff 请求标识 Thread、旧 Ticket、发起 Trigger 和幂等键。若当前 Thread 有多个候选旧 Ticket，或另一个独立 Ticket 仍有需要接收该 Thread 的工作，拒绝自动交接并显示冲突；不得静默结束无关工作。

新请求必须先通过正常 gate/Eval，确定新 Ticket 的 Mandate 和接收范围。准备阶段记录旧 Ticket 的状态、关联 Thread、未完成的 MR/外部工作、待处理 Inputs、待发消息、开放问题和人工 hold。旧工作尚未完成时，不把它表述为成功完成：仅在原请求允许结束旧工作、且没有需人决定的未处理风险时继续；否则保持原状态并说明具体原因。不能由新 worker 接管旧 MR 或工作树而默认获得权限。

## 原子切换协议

以 Thread 为串行化边界，持久化 `handoffId`、旧/新 Ticket、状态、接收世代和单调递增的摄取序号；时间戳不能作为并发顺序。摄取、切换和重复请求必须使用同一数据库事务/条件更新竞争该世代。以下是拟议协议，不是现有 API：

1. **冻结。** 校验当前 owner 与世代仍匹配、没有其他交接；事务中建立 barrier，后续已接收 Trigger 写入 Thread 持久队列但不投递或送旧 Ticket 恢复。记录切换水位 `N`；水位代表本系统摄取顺序，不是飞书服务器顺序。去重仍按 Source 事件 ID。
2. **停止旧侧并生成清单。** 禁止新投递和新自动启动，结束 Assignment 并等待已有 turn、后台作业和子智能体按实际执行器能力停止；已发外部操作的结果必须核对。记录所有已领取、已读、未读、未投递和已 handback 的 Input，区分已回应与待处理。不得因未读释放规则再次送 Eval 或重复执行；切换 Trigger 只在新 Ticket 处理一次。
3. **封存上下文。** 在停止确认后建立不可变清单：Thread 的已保存原始 Trigger（含 ID、顺序、发送者、时间、回复关系和可用内容）、实际发送或待发送的本 Thread 回复及状态、Decision、旧 Ticket 的相关报告与未处理事项、原始记录的分页引用和完整性/缺失标记。对旧 Session 可用的相关对话及工具结果以可读取引用保留，并标明它不等同于飞书聊天；不能把整个跨线程 Session 或凭据无差别注入新 Ticket。大历史通过有界分页按需读取，提供水位、数量和校验信息，不能以截断摘要冒充完整记录。
4. **提交。** 在一个事务内再次校验世代、旧 Assignment 已停和授权仍有效；记录交接清单及新 Decision/Mandate，标记旧 Ticket 为不可恢复的 `handed-off` 终态，移除旧 Ticket 的全部订阅及待启动/投递效果，建立新 Ticket 对该 Thread 的唯一 owner，递增世代，并把 barrier 内已保存的事件按摄取序号交给新 Ticket。先前只作历史上下文的记录不重放为新指令；尚未处理的请求按 ID 明确转移，防止丢失或重复答复。新 Ticket 的启动效果与提交一同持久化，提交后异步执行。
5. **恢复处理。** 新 worker 启动时先读取清单、授权和未处理事项，再消费队列；之后的新 Trigger 只进入新 owner。来源恢复重投的事件按 ID 去重，即使其源时间早于 `N`，也按实际摄取顺序记录并标为迟到。原 Topic 的回复通道保留，但发送使用新 Ticket 的权限和去重键。

切换不能仅依赖「先退订再订阅」两次调用：中间会丢路由或并发双投。已有投递效果在执行前也要验证 owner 世代；仅从订阅列表移除旧 Ticket 不能撤回已排队 Input。交接完成后，旧 Ticket 的所有来源的人工、bot 和 CI 消息均不能恢复或投递给它；相关新事件仍按各自 Thread 的正常准入独立处理，不自动赋权新 Ticket。

## 回复、失败与恢复

- 切换前已确认发送的回复保留回执，不再发送。未发送的旧侧回复在冻结时停止派发：明确撤销或转移给新 Ticket，并保留原去重键和顺序；若发送正在进行或结果不明，先通过可用回执核实，不能并发重发。无法核实时保持冻结并交由人处理，避免重复或误报。
- 冻结前失败不改变 owner；冻结后、提交前崩溃，从持久状态恢复冻结、继续排队并重试停止/封存，不自动恢复旧 worker。提交后崩溃只恢复新 owner 的启动和投递。每一步可重复执行并检查世代，旧效果不得越过 fence。
- 旧进程不能确认停止、上下文不可读、策略失效、多个 owner 冲突或外部副作用不确定时，不提交切换；保留队列和诊断。取消只在能证明旧侧安全、未提交新 owner 时恢复旧侧；否则需人工协调，不能同时重启两侧。队列积压应可观测，并提供明确容量/告警策略，不能静默丢消息。
- 历史缺失要显式标明范围与原因；已有数据不可用时不声称完整交接。权限不足时阻止自动交接或请求有权限的人提供必要信息，不通过其他身份绕过。

## 存量与实现影响

此设计有意改变已结束 Ticket 可随人类消息恢复的规则，仅对被交接的旧 Ticket 生效；普通 ended Ticket 的恢复语义不变。增加持久交接终态和 Thread owner/世代、摄取序号与清单，改造 intake、follow-up ownership、Eval、Assignment 关闭、effect/outbox 与恢复逻辑；面板和资源读取需要显示 owner、状态、队列、冲突及可分页历史。保留旧 Decision、disposition 和输入归属以供审计，不能把现有人工 stop 或删除订阅当作等价实现。

迁移不能直接给历史多订阅 Thread 任意挑 owner：识别并展示冲突，维持旧行为直到明确选择和安全交接。新机制应先在隔离环境和专用测试来源验证，默认关闭，逐步启用；回滚应用版本前需确认旧版本能识别新的终态和队列，否则先安全迁移状态，不能让旧 Ticket 复活。

## 验收场景

- 超出旧 Ticket 授权范围的新请求获得独立授权；新 worker 能分页读取交接前全部可用原文和已发送回复，缺失的消息和图片明确标记，不获得超出新 Mandate 的权限。
- 冻结前、冻结期间、提交瞬间和提交后并发摄取，以及重复/迟到事件和重启重试，逐条验证唯一归属、无丢失、顺序和幂等；旧 worker 不再因任何 Thread 的消息恢复。
- 覆盖运行中的命令、未读 Input、handback、待发/发送不明回复、开放 MR、人工 hold、策略改变和新 worker 启动失败；不产生重复操作或虚假完成。
- 多旧订阅者及历史存量冲突不得自动关闭无关工作；未启用该机制的 Thread 和其他 Git 线程保留原有路由行为。验证上下文访问边界、分页完整性及保留/清理时清单不会悬空。
