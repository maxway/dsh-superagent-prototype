# 011 多 Git 来源

本文评估一个 dsh-superagent 部署能否同时使用多个 Git 来源，或者退一步在来源之间切换，以及多个项目会带来怎样的混乱。文中记录当前行为、假定只有一个来源的各层、可选方案和分阶段建议，不实现其中任何一项。

## 概要

- **今天一个部署只有一个生效的 Git 来源和一个仓库或项目。** 因此一个工单总是只有一个远端、一套准备命令上下文和一个变更请求。`gitProvider` 拒绝两个已配置的 Git 来源，也拒绝一个都没有；另一个宿主的 CLI 被刻意封死。
- **切换已经存在，但它是部署操作，不是界面开关。** 它需要安装目标宿主的插件、切换来源、重启插件，并经过一个暂态的安装配置状态；进行中的派工会中断，旧宿主的工单也不会被迁移。
- **并发多来源在技术上可行，但它是来源身份的一次协同重构，不是改配置。** 核心领域已经在触发、线程和渠道上保存 `source`；问题在于这个标识同时也是来源的“种类”，而许多应用层读取的是一个全局 `Deployment`。
- **如果不在项目层面建立明确的上下文，多项目会混乱。** 这种混乱可控，而且值得在并发之前消除：每个工单、线程、策略项、执行环境、仓库读取和回复都必须携带来源实例。不这样做，飞书请求的路由、`#12` 查找、分支到工单的绑定、权限和检出都会变成猜测。
- **建议。** 先强化切换，同时保持只有一个生效的 Git 来源。如果确实需要并发，先做同一宿主上的多项目实例，再做跨宿主并发。在实例化改造完成前，不要在一个部署里配置两个 Git 来源；第一版也不要让一个工单跨项目。

## 今天部署如何工作

bundle 会安装两个 Git 插件，但默认只启用一个：`cordis.patch.yml` 启用 GitHub、禁用 GitLab；profile 可以同时启用两个插件，但来源设置仍只解析出一个生效的 Git 宿主。相关行为是：

- 安装配置只解析一个 `Deployment`，包含一个 `repository`、一个 `GitIdentity`，GitLab 还包含一个项目 id 和 host。`gitProvider` 返回 `github` 或 `gitlab`，并拒绝两个都已配置的来源或一个都没有。
- 安装配置写一份 worker git 配置、一个该宿主的凭据助手，以及一组命令 shim；未启用宿主的 CLI 在 shim 中直接失败。worker 看到 `DSH_SUPERAGENT_GIT_PROVIDER` 和一个宿主自己的仓库或项目变量。
- 一个来源种类在 `settings.sources` 中只有一份实例配置，以种类 id 为键，只有一条健康条目和一个轮询循环。两个种类都可以注册，但宿主不是当前生效者的种类会把自身挂起为 `sourceOff`。
- 线程键是种类级的：`github:<number>`、`gitlab:mr:<iid>`、`gitlab:issue:<iid>`、`github:ci:<branch>` 和 `gitlab:ci:<branch>`。工单的变更请求从这些键解析，并通过当前生效宿主读取。
- `Commands` 把 GitHub API 路径限制在已配置仓库、把 GitLab API 路径限制在已配置项目 id。评估时的仓库读取也使用同一个部署。

### 切换如何工作，以及它停在哪里

保存来源的启用开关或安装配置读取的字段（仓库、CLI、账号目录）会触发 `Settings.save`；它校验账号并调用 `setup.restart()`。插件重启，安装配置解析新的宿主并重写 worker 环境。旧宿主的记录保留在状态目录中，切回时可以复用已保存的游标和工单。

对切换宿主的人来说，缺口在于：

1. 必须安装目标宿主的插件；默认 bundle 禁用 GitLab，所以从 GitHub 切到 GitLab 的第一步是改 profile 并重启服务。
2. 启用第二个**已配置**的 Git 来源会被拒绝（`multipleGitSources`）。实际操作中，运营者要先停用当前来源，经过一个没有 Git 来源的安装配置状态，再启用并配置目标来源。
3. 重启会中断进行中的派工，并让它们带着恢复说明重新开始。这些工单的来源、工作树远端和打开的变更请求仍属于旧宿主，但 worker 环境已经指向新宿主。因此部署文档要求运营者先完成或停止旧工单；没有任何机制强制执行这一点。
4. 没有逐工单的宿主绑定可以兜底，所以恢复的旧宿主工单无法避免通过新宿主行事。

## “多来源”可以指什么

| 读法 | 例子 | 必须成立的条件 |
| --- | --- | --- |
| A. 切换生效来源 | 部署从 GitHub 迁到 GitLab，或从一个 GitLab 项目迁到另一个 | 同一时间只有一个来源就够；切换要安全，不能把工单搁浅 |
| B. 同一宿主上的多个项目 | 一个 GitLab 实例，同时监听 `team/widgets` 和 `team/service` | 来源实例、逐项目的线程、策略和执行环境；一个宿主账号 |
| C. 多个宿主并发 | 同时监听 GitHub 和 GitLab，二者都能交付 | 在 B 之上再加逐宿主的 CLI、凭据、提交身份、技能和健康状态 |
| D. 一个工单跨项目 | 一个工单同时改库和它的调用方 | 多仓库工作区、多远端提交和变更请求；这是另一个产品决定 |

“同时支持多个不同的项目会混乱吗”问的是 B，部分也涉及 C。D 才是与当前“一个工单、一个远端”设计根本冲突的版本。

## 发现：哪些地方假定只有一个来源

核心的耦合比应用胶水层轻。`Trigger.source`、`ThreadRef.source` 和 `ChannelRef.source` 已经存在，Engine 把它们当作不透明键。下表区分了已经能泛化的部分和假定单一来源的部分。

| 层 | 当前假定 | 多来源需要什么 |
| --- | --- | --- |
| 设置身份 | `settings.sources` 以种类 id 为键；`SourceInstance.id` 就是种类；策略部分和 `source:<id>` 设置块使用同一个键 | 一个独立于种类的稳定实例 id、一个保存的 `kind`，以及让现有设置块继续工作的迁移 |
| 策略 | 允许名单、机器人和接收表按种类保存 | 逐实例策略，让一个项目里获准的人不会自动在另一个项目里获准 |
| 安装配置 | 一个 `Deployment`，一个仓库、账号、提交邮箱和 CLI | 每个 Git 来源解析一套身份（或共享身份加逐实例仓库事实），并逐实例报告安装配置问题 |
| worker 环境 | 一个 `DSH_SUPERAGENT_GIT_PROVIDER` 和一个宿主的仓库或项目变量；未启用宿主的 CLI shim 失败 | 逐工单的来源变量；C 需要两个 CLI 都可用；每个宿主一个凭据助手 |
| 命令层 | API 路径限制在唯一的仓库或项目 id 上 | 绑定到触发或工单所指实例的 `Commands` |
| 轮询 | 每个种类一个循环、一条健康条目、`ctx.config(kind)`、一个 webhook 监听器 | 每个实例一个循环和健康条目；逐项目注册 webhook；GitHub 通知仍是账号级的，但必须按仓库过滤 |
| 线程身份 | `github:12`、`gitlab:ci:main` 等键是种类级的；`find('#12')` 只返回一个线程 | 带实例前缀的键（或实例范围的查找），以及现有键的兼容路径 |
| 变更请求 | `changeOf` 从 follow 键解析宿主；读取和绑定使用唯一的生效宿主；只凭 `pr_number` 就能消歧 | follow 键必须携带实例，读取和绑定必须使用该实例；只有编号的输入在多个项目间无法消歧 |
| 仓库读取 | 评估器通过生效宿主读取一个仓库 | 由触发的实例提供仓库；跨项目读取需要显式指定实例 |
| worker 工具与提示词 | 只注册一个 Git 技能，worker 提示词要求只使用生效宿主 | 逐工单的 Git 技能或环境；C 需要一个技能同时说明实例和两个 CLI |
| 界面 | 每个种类一张卡片，来源、工单和线程视图没有项目维度 | 逐实例卡片、策略部分、健康状态和项目标签或筛选 |
| 运维 | 每个 CLI 一个服务账号、一份 git 配置、一个 webhook 端口 | C 需要每个宿主一个账号；多个项目共享一个监听器但各自注册 hook；逐实例计算限流 |

有两个细节让 B 比 C 小：

- 在同一个宿主上，CLI、配置目录、提交邮箱和 git 凭据助手都可以共享；变化的是项目和 API 路径限制。
- 在两个宿主上，worker 环境必须保持两个 CLI 都可用，而不是让未启用的那个失败；git 配置需要每个宿主一个凭据助手。worker 提示词和 Git 技能也不能再有一个“生效宿主”。

## 各方案的可行性

| 方案 | 可行性 | 主要工作 | 风险 |
| --- | --- | --- | --- |
| A. 强化切换 | 高；小 | 明确的生效来源状态；切换前列出旧宿主的未结束工单并要求显式处理；阻止旧宿主工单对新宿主恢复；用一个切换动作取代暂态的无来源状态 | 低；改变的是运维，不是领域 |
| B. 同宿主多项目 | 高；中大型、需协同 | 实例身份，逐实例的注册表、设置、策略和健康状态，逐实例的轮询和命令层，线程键命名空间和迁移，逐工单的环境和准备上下文，能识别项目的路由，界面 | 中；飞书输入没有项目时会路由错 |
| C. 多宿主并发 | 可行；更大 | 在 B 之上再加两个 CLI 和账号路径、逐宿主凭据助手、逐工单的 Git 技能和宿主变量、逐宿主安装配置问题和限流 | 中高；凭据和身份错误的影响面更大 |
| D. 一个工单跨项目 | 第一版不建议 | 多仓库工作区、多远端提交和变更请求处理、跨仓库 CI 和交付语义 | 高；改变工单契约和准备命令契约 |

对 B 和 C 来说，领域模型没有根本障碍：Engine 已经按 `source` 路由，数据库也保存了这个值。工作量来自应用层——目前“来源”意味着“种类”，“部署”意味着“唯一的 Git 上下文”。一个可信的实现会把来源实例当作单位，并把它贯穿安装配置、命令层、线程、策略和执行环境。

## 混乱问题

直接回答：按今天的隐式模型会混乱；把项目变成显式作用域就不会。多项目本身不会混乱，但如果只改配置层就会混乱。具体的混乱来源是：

| 混乱 | 为什么出现 | 缓解 |
| --- | --- | --- |
| 飞书请求指的是哪个项目？ | 飞书触发不携带 Git 项目；今天只有一个项目 | 要求明确引用项目，或每个群配置默认项目；含糊的请求应当提问或忽略，绝不猜 |
| 两个项目里的 `#12`、`!12` 或同名分支 | 线程键和分支到工单的绑定是种类级的；`find` 只返回一个线程 | 带实例前缀的键和查找；按实例限定自动绑定；每个编号和链接旁显示项目 |
| 检出错误 | 一个准备命令、一个部署级仓库变量 | 逐工单的实例变量；准备命令克隆工单的项目，而不是“那个”项目 |
| 权限泄漏 | 每种来源一张允许名单会适用于所有项目 | 逐实例策略；在一个项目获准的发信人，除非在另一个项目也被列出，否则不在那里获准 |
| 读取错误的仓库 | 评估器读取唯一的生效仓库 | 默认读取触发的实例；读取另一个项目必须显式指定实例 |
| 用错 CLI 或宿主 | 一个生效宿主，未启用的 CLI 失败 | 逐工单的宿主和实例；只有 C 需要两个 CLI 可用；绝不从全局状态推断宿主 |
| 回复到错误的线程 | Outbox 按来源种类解析渠道 | 先按实例解析渠道，再交给该种类的适配器 |
| 一个工单混合多个项目 | 一个工作树、一个远端、一个准备命令 | 保持一个工单一个项目；跨项目请求拆成多个工单 |

每一行的模式相同：把项目变成明确的、被传播的上下文。做到这一点，人能看到工单属于哪个项目，worker 知道该用哪个仓库和凭据，评估器读取正确的文件。做不到这一点，引擎的默认值就会静默地选一个项目，这正是问题所预料的混乱。

## 建议

1. **现在：强化切换，保持一个生效的 Git 来源。** 让生效宿主可见；增加切换前检查，列出旧宿主的未结束工单，并要求显式的排空或停止决定；阻止旧宿主工单对新宿主恢复。这以较低风险交付“可切换”的退路，不引入新的领域模型。
2. **下一步，如果需要并发：同宿主多项目实例。** 引入独立于种类的实例 id，让注册表、设置、策略、健康状态、轮询、命令层和线程键都按实例作用域，增加逐工单的项目变量，并在面板上给出项目标签和筛选。保持一个宿主账号和一个 CLI。这是风险最低、覆盖大多数“多个项目”需求的做法。
3. **然后，只有确有需求时：跨宿主并发。** 增加两个 CLI 和账号路径、逐宿主 git 凭据、逐工单的 Git 技能和健康状态，以及逐宿主的安装配置问题。把 C 当作 B 的第二阶段，而不是另一套架构。
4. **不要从 D 开始。** 一个工单跨项目对执行契约的改变大于对来源模型的改变。在具体工作流证明必要之前，把这类请求拆成多个工单。

合理的顺序是 A、B、C。即使永远不做 B，A 也有用。B 是回答“多个不同项目”而不增加凭据的版本。只有在组织确实同时通过 GitHub 和 GitLab 工作时，C 才值得做。

## 留给运营者的问题

- 需求是同一个 GitLab 实例或 GitHub 组织上的多个项目，还是确实同时使用 GitHub 和 GitLab？
- 当飞书消息没有指明项目时，应该进入配置的默认项目、被拒绝，还是回问一个问题？
- 一个工单是否必须同时修改两个项目？如果是，那就是方案 D，应按 D 设计；如果不是，一个工单一个项目是更简单的契约。
- 允许的发信人和机器人应该是跨项目全局的，还是逐项目的？当前按种类的模型在种类内是全局的；逐实例是更安全的默认。
- 工单运行期间允许切换吗，还是必须等待排空？当前答案是“先完成或停止它们”，但没有机制强制执行。
