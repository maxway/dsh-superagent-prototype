# 003 执行

[English](../003-execution.md) | **简体中文**

本文跟随一个已接单的工单，走过执行、投递和恢复。它建立在 [001 领域模型](001-domain.md) 和 [002 授权机制](002-authorization.md) 之上。

## 工单阶段

每个开放工单都有一个阶段，由它在等待什么决定。从上到下阅读该表；第一个匹配的行生效。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递输入失败；会在 2 秒后重试，之后延迟翻倍、最长到一分钟，一次成功、新的派工或工单结束都会清除它 | 输入未送达 |
| person / answer | 它有一项待人工决定 | 待回答 |
| person / review | 最新的报告是 `ready` | 待验收 |
| person / blocked, failed | 最新的报告是 `blocked` 或 `failed`，且此后没有人的消息到达该工单 | 待处理受阻 · 待处理失败 |
| working / queued | 没有派工，或有一个待启动的派工 | 排队中 |
| idle | 最新的报告是 `waiting`，或派工已结束 | 等待新触发 |
| working | 其他所有情况 | 执行中 |

`person` 阶段意味着工单没有人的输入就无法继续。人发来的新消息会把 `blocked` 或 `failed` 的工单释放给其执行器，因此它会移动到下一个匹配的阶段，通常是 `working`。

`idle` 工单已经结束其回合，且没有悬而未决的问题。已订阅线程上的触发可以继续它。

## 执行器

每个工单会得到一个名为 `worker-<ticket id>` 的执行器 Session，以及一个以工单短名命名的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器 Session 以运营者的操作系统用户身份、无需批准地运行命令。其 `dsh-superagent-worker` 预设包含工作所需的工具，并在 5 秒后把前台 shell 命令移到后台任务。这让执行器（worker）能在下一步接收新消息，而不是等待一条长命令结束。

主 Session 使用 `dsh-superagent-router`，具有相同的 5 秒 shell 和任务等待限制，以及用于路由的较小工具集。Session 会保留创建时选定的预设。执行器的子智能体使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与执行器槽位

当回合结束时仍有 shell 任务或子智能体在运行，工单会保留其执行器槽位并保持工作状态。它不会被报告为等待，主 Session 也不会收到等待报告。一个完成的任务或子智能体会在同一槽位中带着结果唤醒执行器。一旦回合结束时没有后台工作，执行器会正常报告等待。

每个回合结束后，后台工作最多有 30 分钟完成。到达该限制时，shell 任务会被杀死，工单被报告为等待。报告包含执行器最后的话，以及哪些任务被杀死、哪些子智能体仍在活动。子智能体允许继续运行。执行器在下一个回合读取被杀任务的结果。

交给人处理会立即释放槽位，并让报告继续有效。这适用于 `ready` 报告或提问之后（除非此后又到达了另一个输入），也适用于任何 `blocked` 或 `failed` 报告之后。

交接时，子智能体停止。shell 任务，例如为评审而提供的服务器，可以继续运行，直到派工结束。它们不占用槽位，也不受 30 分钟限制，包括在后续回合之后。它们的完成不会唤醒执行器；执行器在下一个回合读取结果。

人也可以直接在执行器 Session 中写消息来启动一个回合。它的后台工作遵循相同的规则。

派工结束时，其 shell 任务会被杀死，且不会唤醒 Session。其子智能体被释放，它们唤醒的任何完成回合都会被丢弃。替代的派工及其等待中的输入会在该关闭完成后启动。

在 DeepSeek Harness 进程内停止或重启插件，会使用相同的关闭路径。尚未纳入 Session 历史的输入会保留。关闭会为每个执行器的后台工作最多等待 10 秒；进程重启会直接终止该工作。在忙碌时被中断的派工会带着恢复说明重新启动。

执行器的子智能体，包括嵌套的子智能体，使用 DeepSeek Harness 的 `standard` 预设，并具有执行器的权限。它们只保留执行器允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令会在 60 秒后移到后台。子智能体的任务在它结束时被杀死。

### 准备工单目录

在第一次派工之前，如果工单目录不存在，prepare 命令会在执行根目录下用 `sh` 运行一次。它有十分钟完成。没有 prepare 命令时，执行器会在一个空目录中启动。

命令失败会使工单失败，并记录其输出。重试或人在工单某个线程上的消息会再次尝试准备。典型的命令使用 `git worktree` 创建一个检出。当 pull request 分支路径的最后一段与工单短名匹配时，该 pull request 属于这个工单。

### 并发

工单从一次启动开始时（包括准备阶段）持有执行器槽位，或从唤醒其空闲执行器的投递开始持有。它在整个活动回合期间也持有该槽位。

配置的并发上限适用于这些槽位，并为人发的消息或状态请求额外保留一个槽位。当正常槽位已满时，这种唤醒可以使用额外槽位，并在新的启动之前先占用下一个空闲槽位。因此，新工作无法阻止人继续一个已有的工单。

其他输入，例如 CI 结果，会等待正常槽位。启动会在 `working / queued` 中等待，直到有槽位空闲。启动并发运行，因此一个慢的 prepare 命令只会延迟它自己的工单。

### 执行变量

prepare 命令和执行器指令收到相同的执行变量。命令读取环境变量；执行器在其提示词中读取它们的值和描述。它们都不包含凭据。

| 变量 | 注册者 | 取值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源监视的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其 commit 邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动该工单的 Issue 或 pull request，以及当它是 pull request 时的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及启动该工单的群 |

工单专属的值来自其目录和起始触发。其他值来自当前的部署设置。只有面板可以更改执行环境设置；发送给主 Session 的文本不能更改已配置的 shell 命令。

执行器通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被阻止的命令在按名称调用时会失败。

这些包装脚本和目录建立的是默认行为，而不是安全边界。执行器仍然可以通过绝对路径执行程序。

## 合并

自动合并由 **Delivery requirements** 提示词管理。宿主没有针对合并的专门决定逻辑。

默认情况下，执行器绝不会以智能体账号启用自动合并：GitHub 会把合并归到启用它的人名下。Delivery requirements 必须指定另一个账号的 CLI 来执行合并。没有指定时，由人合并 pull request。

默认指令只允许对为该工单打开的 pull request 使用自动合并，条件是该 pull request 已就绪、所需的批准覆盖 head commit，并且新增与删除合计少于 200 行。在推送另一个修订之前，执行器会撤回自动合并。

没有正文的评审，例如批准，也会作为触发到达，并可以唤醒正在等待验收的执行器。这些指令约束智能体，而不是 GitHub 的合并规则。要强制执行批准，请在分支保护中要求批准并撤销过期的批准。省略合并 CLI 或删除自动合并段落，即可要求手动合并。

## 工单如何结束

- **就绪但没有 pull request：** `ready` 报告会把工单以已完成结束。
- **无事可做：** 执行器发现没有需要人处理的工作，例如请求无法复现或已被取代，会报告 `dropped`。工单结束且不发消息，除非匹配的规则要求发一条；人之后在其线程上的消息会使其恢复。
### Pull request

一旦其执行器报告，工单就会关注它起始所在的 pull request。一旦执行器报告或 GitHub 来源发现，它也会关注从自己的分支打开的每个 pull request。重新打开的 pull request 会被再次关注。

当工单打开的 pull request 都不再是开放状态时，工单就完成了。如果它没有打开任何 pull request，则它关注的所有 pull request 都必须已关闭。然后它带着最后一次相关关闭的结果结束，并保留其订阅，使之后的人的评论能够恢复它。

当恢复、重试或重启恢复的工作尚未完成时，关闭不会结束工单。如果执行器确认或回复了它拥有的跟进，但此后尚未作出非进展报告，也未在读取该消息后结束回合，关闭也会等待。一旦满足相同的 pull request 完成规则，之后的 `ready` 报告会结束工单。

聊天渠道会收到一条关于 pull request 结果的最终通知。GitHub 已经在 pull request 本身上显示结果。移除工单对某个 pull request 的订阅，也会让它停止关注该 pull request。

因此，「待验收」意味着带 pull request 的 `ready` 报告。

### 跟进与上下文线程

执行器决定其工单自有线程上的人的跟进。它处理范围内的请求，并把超出其范围或属于另一个工单的请求交回。一旦没有执行器拥有该消息，它就成为主 Session 的候选。除此之外，主 Session 只能按人的请求停止工作来处理该跟进。

输入在 Session 将其纳入一个步骤，并且随后作出报告或结束回合之后，才算已读。工单结束时，未经确认、回复或交回的未读消息会回到评估，如 [002 授权机制](002-authorization.md) 所述。已读但未处理的消息，例如感谢，则不会。

仅为上下文而关注的线程仍会投递消息，但不会让工单拥有人的跟进的所有权，也不会恢复已结束的工单。那些消息可以被独立研判。

在有活动工单订阅期间，以及在最后一个触发与订阅工单的结束两者中较晚者之后的两个星期内，来源会轮询已订阅的线程。之后，消息只通过普通入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败或出错（记录为 `failed`）时，工单不接收任何自动输入。

模型提供方或网络的一过性失败、HTTP 408、429 或 5xx，或连接被拒绝、重置或超时，会先再次尝试，最多三次，退避时间递增：启动会重新运行，回合失败的执行器会被要求继续；失败的 prepare 命令不会重试。

一旦失败，CI 和机器人的消息会记录在工单上，但不会投递，也不会唤醒 Session。

它的工具仍然可用，因此人可以直接在该 Session 中继续。

失败的启动不会自行重试。

人的消息、之后一个既不是 `blocked` 也不是 `failed` 的报告，或一次重试，都会结束这种挂起状态。

它由存储的报告和输入推算得出，因此重启会保留它。
### 重试

当开放工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：新的派工会重新启动其执行器并接收等待中的输入，是每种情况的对策。

一旦人的消息到达受阻或失败的工单，执行器就拥有了该消息，因此工单显示为工作中，或在失败的启动重新开始时显示为已排队，并且不提供重试，除非投递该消息失败。

重试会结束当前的派工，并在同一个执行器 Session、目录、分支和 pull request 中启动新的派工。

执行器模型只在创建 Session 时生效；已有的 Session 保留其模型。
### 重启

运行中的派工以「host restarted」结束，新的派工会带着恢复说明启动，该说明要求执行器在重复任何外部操作之前检查其目录、git 历史和 GitHub，最旧的工单优先。

处于等待、就绪、受阻或失败的派工保持原状，除非在该报告之后有输入到达它们，这种情况下它们也会重新启动。

Session、目录、订阅、待启动消息以及下面存储的工作都能在重启后保留，每个执行器 Session 将哪些消息纳入其历史的记录也一样：一个步骤在认领它们之后、调用模型之前完成这件事。被重启中断的回合所取走的消息，在随后出现报告或回合结束时算作已读；而某个步骤已认领、但在写入历史之前被取消或错误中断的消息，算作未读。

重试或重启会把投递给被替换派工、但其执行器 Session 未取走的消息（可能因取消或中断的步骤而被丢弃）再次交给新的派工；仍留在 Session 中等待的副本（由重启保留或跨崩溃持久化）会在新派工的第一条消息之前被取出，因此新的投递是唯一的副本。
### 存储的工作

dsh-superagent 在作出决定之后要做的事，例如把候选、跟进或报告转达给主 Session，启动派工，或投递输入，都会先被存储，然后再执行。

转达或投递失败（例如无法联系到其 Session）会先等待 2 秒后重试，然后延迟翻倍、最长到一分钟；启动失败会使工单失败，除非该失败是上文所述的一过性失败。

每种工作只有在某一项连续失败三次之后，才会在总览的系统问题中报告错误；输入投递失败则显示在其工单上。

发往主 Session 的转达保持其顺序，通知也一样；一个失败的转达会挡住其同类中较晚的转达。
### 来源故障

GitHub 来源会分别读取每个 Issue、pull request 和线程：一次失败的读取会把错误留在其线程上，在下次轮询时再次读取，并计入来源的错误；默认情况下，来源在连续三次轮询失败后报告该错误；任何一次成功的轮询都会重置计数。

当智能体失去对私有仓库的访问权限时，GitHub 也会返回 404，因此 404 会被重试。

被通知的 Issue 或 pull request，如果读取持续失败，会在首次读取失败一天后被丢弃；当 GitHub 报告它已删除时则立即丢弃；之后它不再使轮询失败，其线程保留该错误，来源的状态会列出它。

它的读取位置保持在原处，因此之后的某个通知或对其线程的轮询会读取那些失败的读取所遗漏的内容。

飞书事件消费者会报告每次失败，对已订阅话题的轮询会把每次失败保留在其线程上。

GitHub 列表或飞书页面中格式错误的条目会被跳过，并由来源的状态计入。
### 渠道故障

发出的消息会作为存储的工作被存储并发送，从 5 秒开始退避重试，每次翻倍，直到 300。

工单发往同一个对话的消息按入队顺序发出，因此其确认会先于之后的回答或结果：当同一工单发往同一对话的较早消息尚未发出时，后一条消息会等待，直到那条消息连续失败三次并显示为问题。

其他工单的消息，以及不属于任何工单的消息，不会等待它。

有失败尝试的消息在发出或被撤回之前，都是系统问题。

只有当来源不再监听该对话，或来源答复该对话永远无法接收它时，消息才会被丢弃；其来源关闭期间，它会等待。

来源会对 GitHub 上已删除的 Issue 或已锁定的对话这样答复，也会对撤回的消息，或飞书不再能在飞书上找到的消息这样答复。

对已不存在的评审评论的回复，会改为发到该 pull request 的对话中。

被丢弃的消息保留其记录，包括丢弃的时间和原因，以及它原本所属的工单，因此它永远不会再次入队；被丢弃的确认显示为已丢弃，而不是已发送。
### 暂停处理

停止派发、新的评估、评估超时、输入投递和回复；已经开始的启动会等待，直到处理恢复。

来源会继续记录触发，正在运行的执行器回合不会被打断。

人发给已结束工单的消息会等待：暂停后的第一次处理会恢复该工单，前提是其授权在当时的策略下仍然成立。

进行中的评估在暂停期间不会过期；其截止时间会按暂停的时长向后移动。
### 无效配置

被其类型拒绝的已存储来源配置会禁用该来源实例。
