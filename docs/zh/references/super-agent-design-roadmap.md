# Super-agent 剩余能力落地计划

> 基于 [super-agent-design.md](super-agent-design.md) 和 [能力差距分析](super-agent-design-gap-analysis.md)，把尚未落地的工作拆成可独立交付的工作流和里程碑。基线：`main` @ `e7b6264`（2026-11-09）；Watchdog 只读巡检（MR !28）与独立进程已落地，阶段 2 的 retry/stop 介入（MR !30、!32）已随外部独立 Watchdog 的启用而移除；部署指令与独立执行任务（MR !43）已落地，2026-11-09 的 Windows Job 归属问题由 `scripts/service-start.ps1` 与 `verify` 修复；多 Git 来源方案 A（MR !34）与 Windows 原生部署系列（MR !10–!19）已落地。多 Git 来源的完整现状见 [011 多 Git 来源](../011-multi-git-sources.md)；双向发布与看护的设计见 [Watchdog 与 Superagent 互辅助设计](watchdog-superagent-mutual-assist.md)。

- Windows 原生部署：服务控制、worker 命令层、prepare、router 工具、飞书来源与 CI 均在 Windows 上落地（MR !10–!19），部署现状见 [009 Windows 部署](../009-windows-deployment.md)；它不改变本计划的设计差距，但决定了 5.1/5.2 的现状描述。

尚未完成：

- Watchdog 阶段 3：从 Watchdog 修改设置或提示词。
- Superagent 内的部署入口，以及由独立 Watchdog 执行受控发布和主机服务看护（检查项与有界恢复）：`orchestrator_deploy`、独立 `dsh-superagent-deploy` 任务与 `scripts/deploy.ps1` 已落地（MR !43），部署执行器改为在 agent 退出后做存活校验，P1 已由生产 `verify`（`foreignJob=false`）验证；Watchdog 制品已脱离 checkout。仍未完成：主机检查项、持续 observer 的安装、独立飞书投递，以及部署请求路径与服务环境的一致性（当前生产服务仍指向旧 `watchdog` 路径）。设计与分阶段方案见 [Watchdog 与 Superagent 互辅助设计](watchdog-superagent-mutual-assist.md)。
- 设计第 5 节的两个模块：计算与状态分离（5.1）、计算与执行环境分离（5.2）。
- 投机执行（3.4）、飞书线程上下文、架构级评测、安全与隐私加固，以及可选的邮件/文档信道。
- 多 Git 的 B（同宿主多项目）和 C（跨宿主并发）；D（一个工单跨项目）不在第一版。

计划原则：

- 每个工作流能单独合并、单独验证，不做一次性大改。
- 涉及自动修改状态的阶段先只观察，再小范围执行，默认关闭。
- 先补当前单机部署的可靠性，再启动架构级改造；架构改造先做决策与 spike，不直接进入实现。

## 工作流

### A. Watchdog 阶段 2：介入

> 状态：已实现后移除。`watchdog` 设置块、专用介入 API、SQLite 审计、冷却/限流、retry/stop 与面板表单曾落地（MR !30、!32）；外部独立 Watchdog 可用后，服务内实现已清理，决定与报告归外部进程。本文保留原始任务与验收，作为历史记录。

**目标。** 在只读巡检的基础上，允许 Watchdog 对确认卡住的工单执行 `retry` 或 `stop`，同时保证误操作可审计、可限流、可回退。

**任务。**

1. **设置块 `watchdog`。** 增加 `mode`（`off`、`observe`、`report`、`enforce`，默认 `observe`）、允许的动作（`retry`、`stop`）、每工单每小时的次数上限、全局每小时上限、冷却时间和 `staleMinutes`。设置由面板和 API 校验，`enforce` 需要显式开启。
2. **审计记录。** 每次介入记录快照时间、工单、动作、模型给出的理由与证据、动作前后的阶段、结果和发起者。记录持久化，并在 `GET watchdog` 或单独的只读路由中可查。
3. **介入 API。** 新增专用的 `POST /orchestrator/api/watchdog/tickets/<id>/<action>`，请求体带 `reason`、`evidence`、`snapshotAt` 和幂等键。API 重新读取工单并校验：快照没有过期、工单没有变化、动作仍在允许列表、限流未触发、`mode` 为 `enforce`。通过后调用现有的 `retryTicket`/`stopTicket`，把结果写进审计。
4. **安全前置条件。** 有等待人工的问题（`attention`）、最近有人类跟进、正在投递输入、暂停、安装配置未完成或谷价等待的工单，不执行自动动作；`retry` 只在 `canRetry` 为真时允许；同一工单在冷却期内只允许一次动作；动作失败不回滚工单，只记录并报告。
5. **提示词与文档。** 部署文档的 Watchdog 提示词增加“观察/执行”两种模式：默认只报告；`enforce` 下每个发现最多一个动作，必须带证据，动作后仍要向运营者报告；同一发现没有新证据时不重复动作。
6. **测试。** 设置校验、四种模式、限流与冷却、审计、安全前置条件的拒绝、HTTP 路由、命令与文档测试。

**验收。**

- `observe`/`report` 模式不改变任何工单；`enforce` 下对一个阻塞工单的 `retry` 能让它恢复，且审计可查。
- 有 `attention`、有人类跟进、暂停或安装配置未完成时，API 拒绝动作并记录原因。
- 冷却期内重复调用被拒绝；并发调用只有一个成功。
- `pnpm check` 通过；部署文档给出开启 `enforce` 前的观察期建议。

**风险。** 误停正在等待人的工单、重复重试造成抖动、模型误判“偏离目标”。用默认观察、严格前置条件、冷却和每工单上限控制；先在一个测试项目上跑一周再开 `enforce`。

### B. Watchdog 阶段 3：配置修改

**目标。** 让 Watchdog 能修正提示词或策略，例如增删一条规则、调整研判模式。

**任务。**

1. 定义可修改的范围（提示词段落、策略规则、观察窗口），高风险字段（账号、执行环境、来源凭据）永不允许自动修改。
2. 生成改动草案：展示 diff、影响范围和回滚方式；`enforce` 下也需要一次显式的人工确认，或者只允许“生成草案、由人保存”。
3. 审计与回滚：记录修改前后的版本；提供一键回滚；策略变更仍走现有的 `policyChanged` 通知。
4. 测试：diff、版本冲突、回滚和越权拒绝。

**验收。** 自动修改只发生在允许范围内，且每一步可审计、可回滚；高风险字段被拒绝；默认只生成草案。

**依赖。** A 在 `enforce` 模式下稳定运行至少一个发布周期。

### C. 计算与状态分离（5.1）

**目标。** 让推进 Agent Loop 的计算可以重启、替换或水平扩展，而会话与任务状态由持久化存储保障。

**先做决策与 spike。**

1. 明确目标：只做“单机 + 远程数据库 + 可重启”，还是一步到多实例；多实例需要解决 Router 单 Session 的归属问题。
2. 评估 DSH 的 Session 持久化能力：能否把 Session 日志放到共享存储或数据库；是否缺少删除、迁移或远程读取 API。这是本工作流最大的外部依赖。
3. 盘点当前状态：SQLite 大小、Session 日志、工作目录、锁和租约；给出迁移与回滚的成本。

**实现阶段。**

1. **Store 适配器。** 在 `Repositories` 之后增加 PostgreSQL（或等价）适配器，保持现有 Store 行为；用同一套 conformance 测试跑 SQLite 和远程数据库；补迁移与备份。
2. **状态迁移。** 把 SQLite 数据迁移到远程数据库；处理 schema 版本、迁移失败和回滚；保留导出/导入路径。
3. **Session 持久化。** 按 spike 结论，把 DSH Session 日志迁到服务端或共享存储；若需要上游 API，先提交最小改动，不绕开 DSH 的持久化锁。
4. **无状态运行时。** 把插件打包成无状态容器的启动方式；配置和凭据通过环境或密钥服务注入；健康检查、优雅关停、drain 和启动恢复沿用现有逻辑。
5. **租约与多实例。** 用数据库租约保证同一工单同一时间只有一个执行器；评估 Router 是否需要 leader 或按来源分片；副作用和 Outbox 的所有权必须唯一。
6. **切换与回滚。** 维护窗口、备份、双写或暂停写入、回滚到 SQLite 的路径；上线后验证重启和跨主机恢复。

**验收。**

- 在一个实例上运行中的工单，计算进程被终止后能在另一个实例恢复，状态不丢、不重复执行。
- 两个实例不会同时推进同一工单；租约过期和接管有测试。
- 数据库备份可恢复；迁移和回滚演练通过。

**规模与风险。** 大；分布式锁、Session 一致性和 DSH 上游限制是主要风险。先做 spike，结论不成立就停在“远程数据库”这一层，不承诺多实例。

### D. 计算与执行环境分离（5.2）

**目标。** Agent Loop 可以在云端，执行环境留在用户机器或托管机器上，通过端侧 daemon 执行命令并返回结果。

**任务。**

1. **协议。** 定义命令执行、文件读写、长任务、取消、环境变量和错误返回；明确超时、输出上限和二进制/编码处理。
2. **端侧 daemon。** 不保存会话状态，只持有设备身份和执行权限；支持 POSIX 与 Windows；安装、升级、日志和健康检查。
3. **设备注册与选择。** 设备如何注册、如何授权给某个部署、工单如何选择设备；支持多设备和离线设备排队。
4. **认证与隔离。** 设备与云端双向认证；daemon 只暴露必要能力；不在云端上下文里放设备凭据。
5. **执行器改造。** 把 `DshExecutor` 对本机 Session 和目录的假设收敛到一个可替换的传输层；保留本机执行作为默认实现。
6. **验证。** 用一台测试设备跑完整工单：准备、执行、长任务、取消、断线重连、离线排队；记录延迟和失败模式。

**验收。** 工单能在远程测试设备上完成；设备离线后任务等待并在恢复后继续；daemon 被攻破时不能读取云端状态；本机执行路径不受影响。

**依赖。** C 的完成程度决定云端形态；如果只做单机加远程数据库，D 可以先做“同机 daemon”验证协议，再做跨设备。

### E. 投机执行（3.4）

**目标。** 在决定是否值得交付之前，先在后台尝试；结果有价值就交付，没有价值就丢弃，用额外算力换更短的等待。

**先做决策。** 明确授权边界（谁能触发预执行）、成本上限、失败是否可见、结果如何丢弃，以及它与“只在被请求时行动”理念的关系。

**任务。**

1. 给主动规则增加 `speculative` 配置（默认关闭），限定来源、规则和成本上限。
2. 匹配的触发在评估决定前启动一个可取消的轻量 worker；它不写外部信道、不创建工单、不推送通知，只在隔离目录里工作。
3. 评估 `accept` 时把预执行结果转正；`ignore`、超时或成本超限时取消并清理，保证没有外部副作用。
4. 记录预执行的命中率、浪费的 token、节省的等待时间；用于决定是否扩大范围。
5. 测试：转正、丢弃、取消、超时、成本上限和并发冲突。

**验收。** 默认关闭；开启后丢弃的预执行不留外部痕迹；转正后复用结果；指标可查；失败不打扰人。

**风险。** 浪费算力、与授权模型冲突、用户看到“做过又没做”的困惑。先在一个低风险来源上试点。

### F. 飞书线程上下文

**目标。** 让飞书评估能读取触发前后的消息和所回复的消息，补齐 3.3 在飞书一侧的召回。

**任务。**

1. 决策：申请只读消息/历史权限，还是维持现状。前者需要运营者确认权限面和隐私影响。
2. 若扩大权限：实现飞书的 `threadContext` 读取器，复用现有的上下文读取接口；处理分页、删除消息和权限失败。
3. 若不扩大：在提示词和文档中明确飞书触发缺少线程上下文，让评估更保守；在差距分析里保留这一限制。
4. 测试：上下文读取、权限失败、消息缺失和脱敏。

**验收。** 飞书评估能读到前后消息（或明确记录限制）；不泄露私聊和未授权群的内容；权限失败有健康提示。

### G. 架构级评测

**目标。** 复现设计第 7 节的对比，给双层架构、订阅直通和 Router 批处理一个可重复的量化依据。

**任务。**

1. 合成负载生成器：群聊、GitHub/GitLab 事件、CI 消息、工作请求和闲聊，按可配置速率注入。
2. 对比方案：完整 Super-agent、去掉直通、单 Session + Subagent（中性提示与优先委派提示）。
3. 指标：完成时间 p50/p95、Router 决定数、读缓存 token、batch 大小、单次请求耗时。
4. 用 mock worker 控制执行耗时，只测调度；结果写入文档，脚本可重复运行。
5. 可选：在 CI 之外手动运行，避免拖慢每次合并请求。

**验收。** 一条命令复现实验；文档记录环境、参数和结果；结论与设计的差异有解释。

### H. 安全与隐私

**目标。** 缩小 worker 的凭据和文件访问面，为 5.1/5.2 的跨设备形态做准备。

**任务。**

1. 威胁模型：worker 被提示词注入、仓库内容恶意、设备失陷、云端失陷四种情况。
2. 专用操作系统账号运行 worker；限制主目录和凭据目录的访问；Windows 上明确没有 OS 沙箱的残余风险。
3. 凭据代理：CLI 和 git 通过代理使用凭据，模型上下文不出现 token；评估现有 shim 和 git credential helper 的覆盖范围。
4. 审计：记录 worker 执行的敏感命令和外部写入；为 5.1/5.2 的远程执行预留审计点。
5. 文档：明确哪些是已缓解、哪些是残余风险。

**验收。** 威胁模型和残余风险有文档；worker 不能直接读取运营者的个人凭据；现有部署的默认隔离不退化。

### K. Superagent 部署入口与独立 Watchdog

> 状态：部署请求文件、独立执行任务与 `scripts/deploy.ps1` 已落地（MR !43）；执行器退出后的存活校验和 Job 归属判定已修复，生产 `verify` 于 2026-11-10 以 `foreignJob=false` 通过。版本化 Watchdog 制品、独立更新任务和面板安装/心跳信息已落地（P2）。仍未完成：面板发起部署的入口、部署状态查询与断线恢复；另外生产服务的 `DSH_SUPERAGENT_DEPLOY_REQUEST` 仍指向旧 `watchdog` 路径，与部署任务的 `requestPath`（`watchdog-deploy`）不一致，需在下次启动前对齐。当前生产发布仍由操作员批准维护窗口。详见 [Watchdog 与 Superagent 互辅助设计](watchdog-superagent-mutual-assist.md)。

**目标。** 在 Superagent 面板提供部署入口，展示当前版本、候选版本和部署状态；由独立于被更新服务的 Watchdog 或部署监督器在授权后执行发布，服务停止或重启时监督器仍能继续工作。面板断线后可恢复查看结果，服务无法恢复时也能从监督器侧查询。

**需求与边界。**

1. **申请与授权分离。** 面板提交绑定部署目标、不可变版本或制品摘要和幂等键的申请，并显示影响、维护窗口和状态；不接受面板提供的任意命令、路径或脚本。默认禁用执行，监督器缺失或不可用时明确提示，不能显示为已部署。本机管理 API 的来源检查不是操作员身份认证；监督器必须独立验证授权，不能将面板请求或同账号可读取的令牌当作可信批准。
2. **独立生命周期与权限。** 监督器的进程、配置、日志、锁和持久化状态独立于 Superagent，并在服务重启期间存活；明确 OS 身份、访问控制和部署权限，避免 worker 伪造批准或修改监督器。部署目标采用预先配置的白名单；生产切换须绑定目标、版本和维护窗口，经独立操作员批准。
3. **发布前检查。** 在独立的非生产环境构建并验证候选版本及其依赖，核实目标进程、运行版本、制品完整性、兼容性和活动工作；暂停新派工并确认已有工作已静止。确认停止目标、保留可用旧版本与依赖，取得并验证数据库、配置和必要工作的一致备份；任一前置条件失败或超时均不切换。候选环境不得使用生产状态、凭据或飞书机器人。
4. **切换与恢复。** 监督器持久化部署阶段、结果和审计，使用部署锁及幂等键防止并发或重复操作；只停止已核实的目标。切换后核验实际进程、运行版本、管理 API、来源连接和安全端到端检查。失败时保留现场并报告；回滚前核对数据库兼容性及备份后新增的数据和外部副作用，不盲目覆盖生产状态。不能承诺零停机或消息绝不重复。
5. **待决策。** 明确监督器安装方式和授权机制、可信制品来源、部署状态查询与断线恢复协议，以及稳定 checkout 同时作为生产 bundle 和工单 Git 源时的切换方式；不得假设重命名 Windows 目录后依赖链接仍可用。

**验收。** 未配置监督器或未授权时无法执行；相同申请重试不重复发布，并发申请不互相覆盖；候选验证、备份或停流失败时生产不切换；监督器在服务停止、重启和自身故障恢复后仍能查询状态；用隔离环境和模拟来源验证成功、失败及回滚路径，不触碰生产机器人或工单。

### L. 独立 Watchdog 的主机服务看护

> 状态：基础独立进程已落地（`scripts/watchdog`：工单观测、运行记录、飞书报告、安静日报与独立不可达告警；长期进程用版本化等待跟随工单、健康与静默阈值变化）；`session-missing` 观测与有界恢复也已落地。主机检查项、自监督与 K 的持久部署监督仍待做；持久 observer 尚未安装为常驻任务，当前监控由 30 分钟一次的门控 agent 承担。服务内的 Watchdog 介入设置与审计已移除，只保留只读工单与 service 各部分健康快照；主机侧另有一个计划任务在登录状态下检查 CI runner 的进程（进程缺失时重启，只写本地日志），两者尚未打通。与 Superagent 互相看护、Session 级信号和双向心跳见 M。

**目标。** 当 Watchdog 以独立进程（而不是 DSH 服务内的定时会话）运行时，除工单与部署外，还能按运营者预配置的检查项看护宿主机上的外部服务，例如项目 CI runner：发现进程缺失、健康检查失败或长时间不轮询时，在允许的范围内做有界恢复并留下审计与报告；主服务停止或重启时 Watchdog 仍能工作。

**需求与边界。**

1. **独立生命周期。** Watchdog 的进程、配置、日志与状态独立于 Superagent，主服务重启或故障期间仍能检查主机服务并留下可查询的记录；它自身的安装与故障恢复不能依赖被看护的服务。
2. **检查与动作来自配置。** 检查项（进程、HTTP 健康检查、命令及其超时）和允许的恢复动作由运营者按主机预配置，或经独立运营者确认后生效；不接受工单、面板或消息提供的任意命令、路径或脚本。检查必须幂等且只读，动作必须有界、可审计。
3. **识别真实故障。** 至少能区分进程缺失、进程存活但长时间不轮询、健康接口不可用；对同一故障遵循 observe/report/enforce 模式、冷却与限流，不重复动作，并与现有工单动作共用审计。
4. **报告与去重。** 观察、动作、前后状态和结果进入持久化审计；有要报告的事时仍走飞书汇总。独立 Watchdog 与任何主机侧临时看护（例如当前计划任务）必须明确由谁负责，避免同时重启同一服务。
5. **与当前主机看护的关系。** `dsh-gitlab-runner-watchdog` 只覆盖“进程缺失”这一种情况（登录状态、每 15 分钟、只写本地日志），作为 L 落地前的临时措施；L 落地后应由独立 Watchdog 接管或与其去重。

**待决策。** 独立进程与 K 的部署监督器是否同一进程、检查项的配置格式与授权方式，以及它自身如何被监督和自恢复。

**验收。** observe 模式只观察不动作；enforce 下停止一个测试服务，Watchdog 在配置范围内重启并写审计，超过冷却或限流时不重复；主服务重启后 Watchdog 仍能检查、报告和查询历史；工单或面板不能注入任意检查命令。

### M. Watchdog 与 Superagent 互辅助

> 状态：设计完成；P0（Feishu watch 关闭竞态）、P1（进程归属与存活校验）、P2（版本化制品、独立更新、双向版本/心跳）和 P3（Session 缺失观测、有界恢复、独立告警）已落地并在生产验证；P4（面板部署入口与审批配置）待做。完整设计、目标拓扑、边界与验收见 [Watchdog 与 Superagent 互辅助设计](watchdog-superagent-mutual-assist.md)。

**目标。** 两个独立生命周期：Superagent 可以开发、升级和请求部署 Watchdog；Watchdog 可以受控发布 Superagent、看护服务与 Session，并向服务报告自己的版本和心跳。任一方退出或更新都不连带杀死另一方；生产发布仍由操作员批准维护窗口。

**边界。** 服务永不重启自身；Watchdog 不在服务进程树内；长期进程由计划任务/系统服务启动；双向请求使用文件/API、幂等键、部署锁、版本白名单和持久化审计，不接受任意命令。

**阶段。** P1 修复服务启动归属（执行器退出后服务仍存活）并让当前生产实例在 DSH 之外重启；P2 把 Watchdog agent 脚本入仓、版本化制品、增加独立更新任务和双向版本/心跳；P3 增加 Session 缺失/停摆信号与有界恢复、服务不可用时的独立告警；P4 面板部署入口与审批配置。

**验收。** 更新 Watchdog 不重启服务；执行器退出后服务仍 `ready`；并发请求只生效一个；失败可回滚；杀死测试 Session 后 Watchdog 能识别并报告/恢复；服务完全停止时 Watchdog 仍能工作并在恢复后补齐状态。

## 决策点

在进入实现前需要明确：

1. **5.1 的目标拓扑。** 只做“单机 + 远程数据库 + 可重启”，还是追求多实例。多实例会触及 Router 单 Session 的归属，成本高一个量级。
2. **5.2 的信任模型。** 云端与端侧是否互信；设备失陷时云端暴露什么；首批接入哪些设备。
3. **3.4 的授权与成本。** 谁可以触发预执行、成本上限、失败是否可见。
4. **飞书权限。** 是否申请只读历史权限，还是接受上下文受限。
5. **安全边界。** 专用 OS 账号是否足够，还是要引入沙箱/凭据代理。
6. **邮件/文档是否属于产品范围。**

## 不在本计划

- Router 水平切分、长程记忆、A2A（设计第 8 节的开放问题，尚无方案）。
- 个人助手场景（日程、待办、邮件助理）；当前项目是单仓库的代码协作 Agent。
- 无独立监督、未经授权的生产自动发布与自重启；K 只是待设计需求，在实现并验证前，发布仍由独立操作者在维护窗口执行。
