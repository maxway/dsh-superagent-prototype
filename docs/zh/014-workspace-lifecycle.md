# 014 安全工作区生命周期

状态：**实现中**。当前检出版本以逐工单只读观察替代破坏性清理，并保存最新报告；自动删除、保留策略、归属接管和自动恢复尚未实现。已选策略是对经核实属于 Superagent 的本地资源受限自动清理，并对经核实属于 Superagent 且已合并的远端分支执行条件删除。这不代表该版本已经部署，也不构成生产操作授权。参见 [Session 保留机制](010-session-retention.md)和[worker 交接](012-worker-handoff.md)。

## 现有行为与风险

旧版执行器实现会在工单结束后排队清理，并在宿主启动时再次为已结束工单排队；已部署版本可能仍会这样做。它等待已知工作停止，检查 worker Session 和工单，再检查预期分支、链接 worktree 形态、普通 Git 状态及提交是否能从本地远端跟踪 ref 或工单取回的 ref 到达。它可能强制移除 worktree、删除本地分支和取回的 ref；工单自己的 pull request 已合并时，还可能在比较远端分支顶端与本地 HEAD 后尝试删除远端分支。这些是旧版实现的性质，不代表实际部署情况。检查和删除不是事务：普通状态会遗漏被忽略文件，远端跟踪 ref 可能过期，`--force` 可能删除 Git 原本保护的数据，而先读取远端再普通删除不是比较并交换（CAS）。取回的 ref 是本地的，不能证明远端持久保存。干净结果或工单结束都不能证明没有进程或人员使用目录。现有进程内协调无法隔离其他进程、主机或直接使用 Session 的操作。

旧版启动实现会准备缺失目录，并把现有目录视为已准备好，而不确定其历史身份。此前部署的恢复实现没有执行这些检查。下述候选恢复检查不构成操作系统安全边界：worktree 只隔离源码，不隔离进程或凭据。

## 归属与清点

本部署的运维前提是：其他人员和系统不会操作工单工作区目录，也不会操作准确归属于 Superagent 的工单专属分支和引用。其他 worktree、分支以及 Git 公共仓库是共享的，可能并发变化。这是运维信任前提，不是操作系统强制的隔离，也不能仅凭名称证明归属。无法保持该前提时，不得运行自动删除。

工单、派工和 Session 应与资源区分：worktree 目录及 Git 管理条目；公共仓库和对象；本地分支及工单 fetch ref；远端仓库和分支；未跟踪及被忽略文件、子模块和嵌套仓库；外部任务、进程及其输出；持久应用状态和外部变更请求。它们的所有者和生命周期各不相同。工单结束、交接、合并变更请求或目录名符合约定，都不会转移或消除所有权。稳定检出、其他任务工作树、共享 Git 对象、无关 ref 和其他服务状态绝不是临时空间。

在新工单被接受前配置 `executor.managedRepository` 时，候选实现会记录代次、仓库及预期路径和 ref，在 prepare 前检查它们不存在，并在之后尝试验证链接 worktree、ref、对象 ID 和文件系统身份。检查失败或不完整时保持未知；旧工单不会被接管。这些证据并不完整，不能授权删除。本地 ref CAS 和日志以及远端条件删除辅助函数只是独立组件，尚未连接自动清理；本地组件需要独立强制的排他生命周期和可信 Git 执行器。保留 Git ref 只能保护对象，不能保存工作区或 reflog 历史，且其保留与释放策略尚未实现。

完整的受管理资源记录还必须绑定部署及状态身份、派工、主机身份、来源及远端仓库身份，以及创建时使用的 prepare 配置。记录资源是受管理、外部提供、共享还是未知。谨慎解析符号链接、junction、大小写及跨平台路径；路径字符串或分支前缀本身都不是证明。在副作用前后记录创建和部分失败阶段，但不存储凭据。配置变更不会追溯改变已有资源的所有者。

## 近期：只读对账

候选实现把之前已排队的清理副作用以及启动时重新排队的工作均作为只读清点处理；不删除工作树、分支、ref 或远端分支。对于已清点的工单，它在状态数据库中保存一份带观察时间和工单结束时间的最新观察，并通过工单详情 API 和面板展示。如果工单结束时没有未结束的派工，清点要到下次启动才会入队；清点失败或暂停时也可能没有当前报告。在可以检查仓库时，报告目录、准确的本地分支和工单 ref，以及 Git 是否发现被忽略的条目。已跟踪和未跟踪改动保持未知：自动清点不运行可能执行仓库自定义 clean 过滤器的 `git status`。远端状态、归属以及缺失或损坏仓库的情况仍为未知。它不扫描没有工单的孤立 ref、不检查外部进程、不证明归属，也不记录完整审计历史。报告只是某一时点的观察，不是删除计划或许可；它可能立即过期。Git 运行时禁用可选锁及文件系统监控；清点不执行 fetch、prune 或 prepare。

运维可运行 `node scripts/workspace-inventory.mjs --repo <local-git-repository>`，无需数据库即可枚举已注册 worktree、`agent/` 分支和工单 ref。也可传入 `--db <sqlite-state-file>`，使用静止且一致的数据库快照关联准确的工单 ID、目录名和分支名。工具拒绝存在 WAL 文件的数据库，但该检查无法阻止并发写入；绝不可指向活跃数据库。对 `agent/` 分支，工具还报告已配置的 upstream 及 Git 是否列出其本地跟踪 ref；未列出时显示 `[gone]`。悬空符号 ref 也可能未被列出。这不计算领先或落后状态，可能过期，也不能证明远端分支不存在。名称和路径只是关联线索，不是归属证据；没有 Git 注册的孤立目录不会被发现。工具不执行删除。

历史 worktree 和 ref 通常缺乏可靠来源：只清点，不接管或删除。人员必须对每项资源明确确认身份、归属、使用情况、保存方式和预期操作；即使确认也不能替代未来的技术安全门槛。年龄、名称、工单终态、合并状态或数据库没有记录都不能单独授权清理。自动迁移不得推断孤立资源可以丢弃。回滚不得让旧二进制重放已排队的破坏性副作用或错误解释新状态：应阻止回滚，或先采用单独设计并审计的兼容流程。

## 恢复、交接与复原

在此候选版本之前已接单但尚未启动的工单，包括谷价或排队工单，没有候选版本的创建声明。如果其工作区或 worker Session 尚未创建，启动会安全失败并要求运维排查，不会自动准备目录或创建 Session。升级前应清点这些工单；目前没有实现自动迁移或运维恢复流程。

恢复已有工单前，运维必须核验原 worktree、分支、未提交及被忽略工作、Git 公共目录、Session 工作目录和外部活动。候选实现会在运行 prepare 前记录准备声明，拒绝重建缺失的历史目录，并检查新准备的 Git 工作区所记录的分支和 Git 公共目录路径。当文件系统提供非零身份时，它会记录新工作区目录的设备号和 inode；对于 Git 检出，还会记录规范化的公共及 worktree Git 目录及其身份。之后身份不匹配或工作区出现符号链接时拒绝继续。这些检查不能发现所有替换，例如身份重用；历史声明和没有可用身份的文件系统没有这一基线。中断的准备过程会保留供运维检查。系统检查已有 Session 的创建目录元数据；新 worker 的创建时间可用时也会记录并在后续使用时检查。这个不可变头信息不能证明 Session 当前工作目录：时间戳可能碰撞或被复制，因此无法可靠区分以相同 ID 和 cwd 重建的 Session。公共目录路径或分支匹配同样不能证明仓库身份。对新 worker，候选实现会拒绝在创建前已出现的 Session，也会拒绝返回了其他 Session ID 的创建结果。控制器仍可能在创建期间复用出现的空 Session，因此这些检查不能证明排他创建。持久的逐 Session 创建标记需要经确认的持久化屏障以及跨 Session 和工单存储的故障关闭恢复；该标记尚未实现。已有目录的旧工单仍可能在可用检查后恢复；它们没有可信基线，不会被自动接管或证明安全。只能通过已核实的原始资源或已知良好的备份，经运维明确协调后恢复，再对账外部变更。即使无法恢复，也要保留旧 Session、报告和来源记录，并如实报告缺失数据。

交接不等于资源转移。现有能力档位交接比 [012](012-worker-handoff.md) 提议的协议更窄：不要假定它已停止每个进程，或已分配旧 worktree、分支或远端变更请求的所有权。继任者不会自动获得修改或删除这些资源的权限。未来任何转移都需要明确授权、持久的所有者/代次变更、经验证的静止状态和一致清单；外部副作用不明确或仍在进行时需要人工处理。

## 未来破坏性生命周期——前提，而非实施计划

删除是独立的可选功能，需要产品和运维明确批准、独立的资源级策略、审计、试运行、保留及恢复设计。在此之前，不承诺自动删除 worktree、分支、ref、Session、数据库或远端资源。工单可能先恢复状态，排队的启动才等待清理，而直接向 Session 输入会绕过该等待。异步 Git 命令前重新检查空闲状态并不是围栏。完整协议需要与工单状态变更协调的持久声明，以及覆盖所有 Session 入口的宿主强制闸门，并保持至 Git 进程退出且结果已记录；崩溃后的未知结果需要对账，不能依靠租约过期解锁。拟议删除协议至少必须：

1. 获取由资源代次防护的持久排他生命周期声明，并跨实例序列化启动、恢复、交接、创建和清理。每项不可逆操作前立即重新读取身份和状态。租约本身无法阻止不配合的外部进程；不能证明排他性时应保留并升级处理。
2. 确认所有者、授权以及准确的仓库、worktree 和 ref 身份；不得有仍需要该资源的活跃或待处理派工、Session 轮次、子智能体、受管任务、交接、输入或恢复声明。尽可能清点独立启动的进程、打开的文件和外部使用者。受跟踪任务停止、PID 不存在或 Session 空闲都不能证明没有脱离管理的进程；证据不全时需要人工协调，而不是大范围杀进程。
3. 清点已跟踪、未跟踪**及被忽略**的文件、嵌套仓库、子模块、符号链接和生成产物，包括密钥和不可替代的本地数据。被忽略不等于可丢弃；不能仅凭普通状态强制删除或执行 `git clean`。保留每一类数据或取得明确授权；遇到未知情况或竞争时阻止操作。
4. 删除本地 ref 或 worktree 前建立独立、持久的恢复能力。保护 ref 应在专用受管命名空间中保存准确对象 ID，以预期旧值检查创建，绑定持久归属记录，并保留到明确释放策略满足为止。保护提交不能保存未提交、未跟踪或被忽略文件、子模块仓库、外部产物或远端可用性；它不是完整备份。Git GC、重新打包和共享对象库必须尊重该保护。绝不能覆盖或删除无关 ref。
5. 将本地和远端删除视为独立操作。确认远端仓库身份、分支归属和真实预期远端对象 ID；仅通过服务器强制执行的条件更新删除（对 Git，在支持时使用带明确预期 OID 的 `--force-with-lease` 删除）。预先 `ls-remote` 再普通删除不是 CAS。远端结果发生变化、不存在、不可访问或不确定时，需要重新观察并明确解决，不得盲目重试。受保护分支或无法执行该条件的提供方保持不变。
6. 在每次副作用前后持久记录意图、预期身份和 OID、授权、逐步结果及持久审计。明确建模部分完成：远端删除、本地 worktree 移除、ref 删除和状态更新不能组成一个事务。崩溃后检查实际状态并幂等对账；外部结果未知时需要人工审查，绝不能从尝试执行命令推断成功。所有必要结果均经验证前，不得将多步操作标记为完成。

远端归属必须独立于来源观察建立：`own` 跟随、匹配的分支后缀或观察到的 source OID 都不能证明独占归属或提供方合并时的 OID。未来协议需要持久证明受控创建了准确提供方仓库中的准确 source ref，获得权威的合并时 source 和 target 身份，并独立验证目标结果。条件删除只保护预期 OID；它不能阻止 ABA 式重新创建，也不能证明仓库身份。

回收目录重命名并非跨文件系统普遍原子，也可能破坏 Git worktree 管理路径；它不是通用撤销机制。备份一致性、受保护 ref 和密钥的保留、磁盘容量、垃圾回收及恢复测试都需要单独设计。年龄或大小阈值绝不能覆盖归属、进程或数据安全。删除 Session 还需要受支持的 DSH 持久化 API，并与锁及工作区注册表协调；手工删除文件不是安全替代方案。

## 任何上线前的验证

使用隔离的测试仓库、home、状态、凭据和进程，绝不使用生产数据。覆盖只有被忽略数据的情况、子模块和嵌套仓库；符号链接/junction 和大小写别名；归属未知的旧 worktree；过期的跟踪 ref；读取与删除之间的远端分支移动；并发恢复、交接和直接使用 Session；脱离管理的外部进程；配置或 Git 宿主变化。在每次持久写入和外部副作用前后注入崩溃，包括远端响应丢失和本地部分移除；验证故障安全、幂等性、审计和回滚兼容性。确认升级后已排队的旧副作用不能删除、只读扫描不修改资源、所有破坏性操作默认禁用。部署和生产观察需要单独明确请求。
