# 010 Session 保留机制

候选版本不会自动删除已结束工单的 worktree、本地分支或远端分支。本文记录保留问题及历史提案，并非已实现的清理策略。`docs/013-workspace-lifecycle.md` 说明当前检出版本的只读对账及其局限。不要假定候选版本已部署，也不要假定拟议的删除或恢复机制已存在。

## 什么在增长

一个工单可能留下 worker Session、工作目录及编排记录。其他 Session、工作区注册表和投影缓存也会增长。2026-11-05 的一次观察中，本部署有 21 个 Session 日志（13.2 MB）、八个工作目录（188 MB）、312 KB 数据库和 4 MB 预写日志。这些是历史测量值，不代表当前容量，也不证明数据可以丢弃。

| 制品 | 常见位置 | 保留注意事项 |
| --- | --- | --- |
| Worker 和编排 Session | DSH home 下的 `sessions/` | 恢复和审计可能需要对话及工具结果。 |
| 其他 Session | DSH home 下的 `sessions/` | 个人和子智能体 Session 不一定属于工单资源。 |
| 工单工作目录 | `<stateDir>/work/<name>` 或配置的目录 | 可能包含本地提交、未跟踪和被忽略的数据、子模块及外部进程输出。 |
| 编排数据库 | `<stateDir>/orchestrator.sqlite` | 工单、派工、触发、决定、副作用和回执历史的依赖各不相同。 |
| 工作区注册表和投影缓存 | DSH home 下的 `storages/` | 必须与 Session 生命周期保持一致。 |

## 现有清理不是安全保证

旧版实现为已结束工单排队清理，包括在启动时再次排队；已部署版本可能仍会这样做。满足其检查时，它可能强制删除链接 worktree、本地分支和工单取回的 ref；工单自己的 pull request 已合并时，它还尝试删除远端分支。普通 Git 状态检查不包含被忽略文件，本地远端跟踪 ref 可能过期，远端读取和普通删除也不是原子 CAS。它无法证明外部进程或人员已停止使用目录。因此，Git 状态干净或提交可达都不能证明不会丢失工作。部署状态可能与当前检出不同；得出运维结论前应单独核实。

旧版启动路径在工单目录缺失时可能运行 prepare，或把现有目录视为已准备好。这两种行为都不能证明恢复安全。候选实现拒绝重建缺失的历史工作区；恢复已有工单前，运维仍须核验原目录、仓库、分支、本地工作和 Session 工作目录。不要假定当前 prepare 设置能够还原以前的工作。

## 保留提案已推迟

本文早期版本提议 45 天后清理工单或 Session、每日清扫、12 小时回收窗口、固定保留、容量上限和回执清理。这些都不是已实现的保证或已批准的策略。年龄、合并的 pull request、干净状态或回收目录重命名均不能单独授权删除。考虑破坏性保留策略前，必须解决 `docs/013-workspace-lifecycle.md` 中的安全、归属、备份、进程、并发和崩溃恢复要求。历史工作区或其他残留需要人工明确确认，不能自动接管或清理。

未来清理 Session 需要受支持的 DSH 删除 API，协调持久化写声明、Session 代际、工作区成员及归档状态和投影缓存。归档只是隐藏 Session，不会回收其存储；绕开 DSH 删除文件会引入竞争和状态不一致。拟议的新 Session 无法恢复丢失的对话，报告或摘要也不等同于该历史。清理回执还需要来源重投和去重窗口的证据；本文未确定固定过期时间。
