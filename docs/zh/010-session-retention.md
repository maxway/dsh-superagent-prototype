# 010 Session 保留机制

dsh-superagent 会保留它产生的几乎一切。一个工单会留下一个 DSH Session、一个仓库工作目录，以及编排数据库里的若干行；当执行器能证明不会丢失本地工作时，它现在会删除已结束工单的工作目录，但没有任何东西删除它的 Session 或数据库行。[007 架构](007-architecture.md)记录了数据库这一侧——"目前还没有删除旧记录，所以这些会无界增长"——DSH 的 session 后端则记录了文件这一侧：session 日志会一直留在根目录下，直到被外部删除，持久化接缝没有删除 API。本文度量这种增长，对照其他系统的做法，并给出一个刻意做小的保留机制：一条规则、一次清扫，以及让删除值得信任所需的最少安全检查。

## 概要

- **什么在增长。** 每个工单一个 `worker-<ticket>` Session，加上部署的编排 Session；每个工单一个工作目录；每个触发、处置、决定、线程、工单、回执和存储值对应的行；DSH 工作区注册表；以及投影缓存。撰写本文时，本部署有 21 个 session 日志（13.2 MB）、8 个工作目录（188 MB），以及 312 KB 的数据库和 4 MB 预写日志。占空间的是工作目录；Session 很小。执行器现在会删除干净且每个提交都在远端的已结束工单工作目录，因此只会剩下仍有本地工作的目录。
- **规则。** 工作目录部分已经实现：已结束工单的链接 worktree 和本地 `agent/<name>` 分支，在 `git status --porcelain` 为空、且每个提交都在远端分支或工单取回的 ref 上时删除。本文其余部分提议在更晚的时候（45 天）清理仍然存在的制品：工单行、报告和线程订阅保留，所以工单仍然可以恢复。
- **清扫。** 已实现的清理是每个已结束工单一个持久副作用，并在宿主启动时再次检查；拟议的每日清扫会覆盖更广的清理。每天一条索引查询、每个候选一次安全检查、一次原子 rename 进回收目录，宽限 12 小时后在后台删除。不新增表，不扫全量。
- **不做什么。** 不做温归档层、不写上下文摘要、不做逐文件 LRU、不清理触发或设置、不轮转编排 Session。这些都在初稿里；按今天的规模，每一件都多一个活动部件而没有相称的收益，因此列为推迟项。
- **可靠性。** 先跑 dry-run；可以 pin 例外；每次删除都重新检查没有工作在运行、没有未推送的工作；回收宽限期保留反悔窗口。唯一的上游依赖是 Session 删除 API。

## 今天在增长什么

下表中的每个制品都能活过重启。目前只有工作目录有保留路径，其余都没有。

| 制品 | 位置 | 增长方式 | 今天会删除吗 |
| --- | --- | --- | --- |
| 执行器 Session | `~/.dsh/sessions/<规范化 cwd>/worker-<ticket>/` | 每个工单一个；随每一轮和每个工具结果变大 | 不会 |
| 编排 Session | `~/.dsh/sessions/<规范化 cwd>/orchestrator-<deployment>/` | 一直只有一个，永久保留 | 不会 |
| 其他 Session | `~/.dsh/sessions/<规范化 cwd>/session-<uuid>/` | 人在 Web UI 中每开一个 Session，或每个子智能体创建时各有一个 | 不会 |
| 工作目录 | `<stateDir>/work/<name>`，或 `executor.directory` | 每个工单一个；一个仓库加上依赖和构建产物 | 工单结束时：没有本地工作的链接 worktree 会被移除，本地分支也会删除；否则不会 |
| 编排数据库 | `<stateDir>/orchestrator.sqlite` | `trigger`、`disposition`、`thread`、`ticket`、`decision`、`effect`、`outbox` 和 `kv` 行 | 不会；只有活跃工作集建了索引 |
| 工作区注册表 | `~/.dsh/storages/workspace.json` | 每个工作区一条记录和一个 session id 列表；每次修改整份重写 | 不会 |
| 投影缓存 | `~/.dsh/storages/session_projcache/` | 每个 Session 一个派生文件 | 会被替换，不会被回收 |

每个 Session 是一份压缩的只追加代际文件，外加一个锁文件；已提交事件从不重写。注册表决定一个工作区列出哪些 Session、哪些被归档。数据库是一个 WAL 模式的 SQLite 文件，用生成列让各轮处理只扫活跃行。字节主要花在工作目录上。

人在 Web UI 中打开的 Session 不是工单包。本提案不归档也不删除它们；那应由 DSH 层面的策略或运维负责。

| 指标（2026-11-05） | 数值 |
| --- | --- |
| DSH session 日志 | 21 个文件，13.2 MB |
| 工作目录 | 8 个目录，188 MB（每个 5.2–139 MB） |
| 编排数据库 | 312 KB 加 4 MB 预写日志 |
| 工作区注册表（整机共享） | 12 个工作区，15 个 session id，0 个已归档 |

最大的工作目录里有 133 MB 是 `node_modules`；工作目录中位数约 6 MB。编排 Session 八小时时是 0.3 MB，较早的部署三天时是 0.7 MB。Session 在工具密集的工作到来之前都不大，之后单个工单可以达到数 MB——这里最大的是 4.3 MB。

## 其他系统如何限制它

每个成熟系统都把保留当作一项策略：两个独立的触发条件，加一条保护活跃工作的删除路径。

| 系统 | 机制 | 对这里的启示 |
| --- | --- | --- |
| [logrotate](https://man7.org/linux/man-pages/man8/logrotate.8.html) | 按时间或大小轮转、压缩、保留 N 代 | 限制代际数量；压缩已经在用 |
| [systemd-journald](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html) | `SystemMaxUse` 和 `SystemMaxFileSize` 限制磁盘；`--vacuum-size` 事后回收 | 磁盘预算，可以带外执行 |
| [Prometheus](https://prometheus.io/docs/prometheus/latest/storage/) | `--storage.tsdb.retention.time` 和 `--storage.tsdb.retention.size`；按整块删除 | 时间和大小是同等触发条件，绝不扫活跃存储 |
| [Elasticsearch ILM](https://www.elastic.co/guide/en/elasticsearch/reference/current/index-lifecycle-management.html) | hot → warm → cold → delete 阶段 | 这里不做分层：见下文 |
| [Kafka](https://kafka.apache.org/documentation/#configuration) | `log.retention.hours`、`log.retention.bytes`；删除已关闭的段 | 删除整单元；绝不重写活跃日志 |
| [GitHub Actions](https://docs.github.com/en/actions/learn-github-actions/usage-limits-billing-and-administration) | 产物和日志默认保留 90 天；缓存按仓库限额，连续 7 天未用被逐出 | 安全默认值加硬上限 |
| [Amazon S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html) | 生命周期规则先转储再过期 | 明确、可审阅的规则，而不是脚本 |
| [SQLite](https://sqlite.org/lang_vacuum.html) | `auto_vacuum` 和 `incremental_vacuum`；WAL 检查点 | 小步回收空间，而不是阻塞式 `VACUUM` |

反复出现的五条规则：

- 两个触发条件——时间和总量——谁先到谁生效。
- 用原子 rename 按整单元删除，在后台进行，绝不截断活跃数据。
- 从索引里选候选；一次清扫的成本是 O(批)，不是 O(全集)。
- 每次运行用批量、耗时和 IO 优先级设上限。
- 保留宽限期、pin、dry-run 和审计，让删除可复核。

## 建议的机制

一条规则、一次清扫、一条删除路径。其余一切在证明必要之前都刻意不做。

### 规则

工单可清理的条件是：结束至少 `purgeDays`（45）天、未被 pin、没有待启动或运行中的派工、没有未投递的输入、没有运行中的智能体。工作目录还要额外满足 `git status --porcelain` 为空，并且每个提交都在远端分支上或对应合并请求已合并；不满足这项工作检查的工作目录会被保留并记录，而它的 Session 仍可单独清理。每个制品按自己的检查独立清理。

### 清扫

清扫每天运行一次，单飞，在模型轮次和面板请求之外。一条索引查询选出超过截止时间的已结束工单。现有 `ticket` 表增加生成列 `ended_at`（`value ->> '$.ended.at'`）和索引，再加一列生成列 `pinned`；`outbox` 增加 `sent_at`，这样已落定的回执可以按索引删除。不引入新表。

对每个候选，清扫重新读取工单、套用规则、把工作目录移进 `<stateDir>/trash/<ticket>-<timestamp>/checkout` 并记录。同一次运行的第二阶段删除超过 12 小时的回收项。运行到批量或时间上限停止，并把数量和字节写进健康条目和日志。

### 工作目录

工作目录才是收益所在：这里有 188 MB，而 Session 只有 13 MB。已实现的清理会在工单结束且安全检查通过后立即删除它，恢复的工单会用 prepare 命令重建。拟议的扩展是加一个回收目录步骤，并为提交尚未全部到达远端的目录保留 45 天兜底，由清扫保留并报告；该扩展尚未实现。

### Session

Session 很小，删它是 DSH 不支持的部分。阶段 2 通过下面描述的 API 删除，同一次清扫调用它。在那之前 Session 会保留，所以 session 列表会继续变长，但磁盘不会因它们出现风险。不用归档替代：归档会隐藏 Session，并在恢复前阻止它运行，却不回收任何空间。

Session 被清理后，投递会为该工单新建一个，派工文本会重新发送，面板保留最新报告；工作可恢复，但对话不可恢复。这是 45 天时接受的取舍。

### 回执与大小上限

两条更小的边界，各自是同一次清扫里的一行。已落定的 outbox 回执在落定 15 天后删除；回执只用于防止重复投递，而来源的重投窗口远短于此。如果状态目录超过 10 GB，本次清扫改用 `emergencyDays`（22）——默认年龄的一半。上限降低年龄，不挑选受害者，所以没有 LRU。如果在减半年龄下仍然超出，健康条目会报告，由运维调低 `purgeDays`。

### 哪些不做

- **温归档层。** 它隐藏 Session 却不回收空间，而且归档的 Session 在恢复前不能运行，恢复要多一步而收益很小。
- **被清理 Session 的摘要。** 它保留上下文，但要多一个 schema 字段、一条写路径和一条恢复路径；45 天时最新报告通常够用。
- **清理触发、处置、决定和 `kv` 版本。** 数据库只有 312 KB；等它以 GB 计时再说。
- **编排 Session 轮转。** 它的日志八小时 0.3 MB、三天 0.7 MB。
- **逐文件 LRU。** 大小上限已经限制住目录；LRU 只决定谁先出局。

### DSH 需要补什么

DSH 没有 Session 删除 API，归档也替代不了它：已归档的 Session 仍占磁盘，而且它的 id 必须先离开归档集合，用同一个 id 重建的 Session 才能运行。绕开 DSH 删文件还会和持久化锁、工作区成员关系以及投影缓存竞争。

最小的正确改动是在 session 持久化接缝上增加一个删除操作：取得写声明，在另一个进程持有时拒绝；删除该 Session 的各代文件和锁；把 id 从工作区注册表的成员关系和归档集合中移除；删掉投影缓存项；返回释放的字节数。dsh-superagent 随后从清扫调用它。阶段 2 等它；阶段 1 不需要它就能上线。

## 性能

- 选择是一条索引查询；不新增表、不扫 session 根目录、不逐候选遍历目录。
- 删除和热路径解耦：O(1) 的 rename 立即返回，删除在宽限期后、一次一个目录、以低 IO 优先级进行。
- 清扫每天一次、单飞、有批量和耗时上限，并在启动和关闭期间跳过。
- 回执删除走索引、分批执行；不对活跃数据库跑 `VACUUM`。
- session 列表在阶段 2 之前不会缩短，但列表成本和今天一样，工作目录也不影响它。
- 清理后的恢复会慢一次：prepare 重建工作目录，或新建 Session；两条路径都不引入新依赖。

## 安全

- 永不删除运行中或待处理的工作；每个 await 之后都重新检查，因为人可能在清扫过程中恢复工单。
- 回收目录是反悔窗口：`trashGraceHours` 内不 unlink 任何东西，运维可以手工还原一次 rename。
- 第一种模式是 dry-run：它记录将要移入回收和删除什么及其大小，除标记外不写任何东西。
- 运维可以 pin 工单，在取消 pin 之前豁免它。
- 未推送的工作永不删除；未通过干净且已推送检查的工作目录会被保留并报告。
- 每次清理留下一条审计行，含时间、原因和字节；健康条目报告最近一次运行。
- 失败的删除会记录并跳过；一次失败不阻塞批次中其余项。

## 默认值

| 设置 | 建议 | 理由 |
| --- | --- | --- |
| `mode` | `off` | 删除有破坏性；dry-run 之后再启用 |
| `purgeDays` | 45 | 原季度的一半；仍足够等一次后续追问 |
| `trashGraceHours` | 12 | 半天用来撤销误操作 |
| `receiptDays` | 15 | 原一个月的一半；仍长于任何来源的重投窗口 |
| `maxBytes` | 10 GB | 原预算的一半，适配这台 1 TB 主机 |
| `emergencyDays` | 22 | 清理年龄的一半，超上限时使用 |
| `batchSize` | 50 | 适合每天五分钟的一次清扫 |

## 阶段

| 阶段 | 范围 | 风险 | 大致工作量 |
| --- | --- | --- | --- |
| 1 | 工作目录删除、回执删除、清扫、dry-run、健康 | 低 | 2–3 天 |
| 2 | 通过 DSH API 删除 Session | 中 | 2–3 天 |

## 备选方案

| 备选 | 为什么不选 |
| --- | --- |
| cron 加 `rm -rf` | 会和活跃 Session 与工作竞争，无法遵守锁，也失去反悔窗口 |
| 只归档 | 隐藏了列表但保留每个字节，而且归档的 Session 在恢复前不能运行 |
| 工单结束即删除 | 对干净且提交全在远端的目录已经实现，prepare 命令可以重建；仍有本地工作的目录会保留。拟议的 45 天清扫会处理其余情况 |
| 外部对象存储 | 对单主机来说活动部件太多；部署变多时再考虑 |
| 仅靠文件系统配额 | 到达上限时让智能体停摆，而不是优雅逐出 |
