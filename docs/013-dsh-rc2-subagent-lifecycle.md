# 013 DSH 0.2.2 rc.1 / rc.2 Subagent Lifecycle Comparison

Status: **Historical investigation and a minimal compatibility candidate, not deployment authorization**. Production processes, configuration, and the deployed version have not been inspected. The investigation below records earlier experiments and is retained for reference; its implementation and quarantine statements describe an archived candidate, not the current working tree.

## Minimal Candidate

The current candidate retains the rc.1 release path. On rc.2 it lists catalogued descendants, interrupts child entries with ancestor authority, and waits for tree work within the existing timeout; it does not drain the reusable worker root. At the user's explicit choice this is best effort, not equivalent to release: local activations and pending inboxes can remain or wake later; catalog gaps, in-flight creation and timeout can leave work running. The rc.2 catalog requires `sessionQuery` and the subagent catalog projection; failure to list rejects the stop. Fixed-version isolated contracts exercise the real runtimes with in-memory substitutes: rc.2 external-child interruption and subsequent delegation, plus rc.1 waiting and a separately mocked rc.1 release path. A real provider, full profile, GUI, and crash recovery have not been validated. The local baseline `9d817fa` removes automatic worktree cleanup; the authenticated remote was not independently verified. Earlier experimental bridge, quarantine and receipt implementations are preserved in a Git stash, not integrated or included in this candidate.

## Conclusions and Scope

This project's [package.json](../package.json) uses `^0.2.2-rc.1` for the DSH `engines` and peers, while development dependencies are pinned to `0.2.2-rc.1`; the locally installed subagent package is also rc.1. An allowed version range does not imply verified compatibility. In rc.2, subagent ownership changes from nested parent-child activations to unified ownership by the tree root: **an intermediate creator can settle while its descendants continue running**. This project currently releases only specified direct subagents when an Assignment ends, keeping the worker reusable; rc.2 lacks the original API. Replacing it directly with a whole-tree drain also closes that root to subsequent subagent admission, so it is not an unconditional equivalent.

## Upstream Facts: Behavior and Interfaces

| Aspect | rc.1 | rc.2 |
| --- | --- | --- |
| Completion and ownership | A local activation settles when its own activity, pending input, **and owned descendants** finish; releasing the activation waits for descendants and resources, children first. | Each instance is owned by the same live tree root; a member settles when its own activity and pending input finish, **without waiting for or stopping descendants it created**. Structured results no longer require descendants to be released either; a dependency on descendant results requires an explicit wait. |
| Host waiting | `waitForChildren(parent)` joins ongoing descendant work and cleanup. | `waitForTreeWork(root)` joins work and cleanup in the tree; ordinary members return false. Neither treats idle instances with only a parked inbox as ongoing work to wait for. |
| Release | `drainChildren(parent, childIds)` releases selected direct children without closing other admission under that parent; `drainDescendants` closes the specified parent scope. | The service interface no longer provides `drainChildren` or `listChildren`; `drainDescendants([root])` closes admission to the selected exact tree root, stops all members, and waits for startup and cleanup. This cutoff lasts until that root leaves the registry; an ordinary member is not a tree root and cannot be used for a local tree drain. |
| Discovery and communication | `listChildren` reads the direct-child directory; `listDescendants` discovers recursively. Model messages are limited to direct parents and children, with cold recovery of direct children. | `listDescendants` discovers recursively; names are unique among siblings, with root `lead` and slash paths. An online root or member can contact other members of the tree that can continue; only the target is recovered, not its creator ancestors. The directory records historical relationships, not a list of running Agents. |
| Notifications and interruption | Parent delivery provides settlement notifications; interruption sends a signal and does not imply convergence. | Completion notifications go to the direct creator only while it remains online; an offline creator is not cold-recovered. Interruption still does not release the whole tree. Lifecycle events are dispatched in tree-root scope rather than creator-parent scope; events are an observation interface, not a completion-decision protocol. |
| Persistence and external execution | Local children can continue; an external provider executes once. In-process activations and inboxes are not coordinated across processes. | The same boundaries remain; directory v3 writes names and reads older directory versions. External execution still accepts no subsequent input. Accepted messages not yet written to the log are not automatically replayed after a crash. |

Both versions restrict the caller's signal to work before publication; release of a published execution is governed by mechanisms such as the activation's `dispose()`. In rc.2, `dispose()` stops only that instance and must not be assumed to terminate descendants recursively. `interrupt` retains the local activation and unclaimed inbox, so it cannot prove cleanup at Assignment completion. In rc.2, cleanup failure causes `dispose()` to reject and marks the end event as failed, but the execution result and parent notification may retain the captured result; a successful result must not be equated with successful resource cleanup.

## Official Design Statements and Inferences

**Sourced official statements:** The rc.2 release notes describe support for named, multi-level SubAgent collaboration; AgentTeam switches to unified named subagents, the interrupt tool is disabled by default, custom plugins and SDKs must migrate, and processes sharing session storage should upgrade together. The rc.2 package documentation explicitly describes unified management of startup, message admission, capacity, runtime ownership, and release; fulfillment means acceptance and that the handle can be cancelled. Descendants run independently after a parent exits, and the host must drain the whole tree before releasing the root handle. It also explicitly states that cross-process sharing requires a persistent mailbox and lease protocol, and that this coordination is currently absent.

**This report's inference, not an official statement:** Tree-root ownership, together with messaging across the same tree and cold recovery when an intermediate creator is offline, supports multi-level collaboration and prevents work from disappearing when an intermediate member settles; however, it shifts responsibility for explicitly waiting for descendants, aggregating results, and terminating the root to the host. The named directory improves addressing and discovery, but directory membership, runtime state, and authorization must be assessed separately. The above upstream sources do not explicitly explain all the tradeoffs behind removing `drainChildren`, nor can improved security or backward compatibility be inferred solely from the name change.

## Project Code Paths and Risks at Initial Review

1. [background.ts](../src/executor/background.ts) selects `waitForChildren ?? waitForTreeWork` for `childrenEnd`, providing a name-level fallback; however, the old and new waits differ in scope and still need validation against the real root, parent idleness, notifications, and Session sequence numbers. `untilQuiet` does not check Session sequence numbers, whereas rc.2 documentation recommends that headless hosts alternate waiting with checks for an unchanged sequence number. There are potential races with completion notifications and risks of prematurely releasing the slot or reporting a waiting state; these require tests rather than a claim that they have been reproduced.
2. In the same file, `stopSubagents` proceeds only when both `listChildren` and `drainChildren` exist. The rc.2 service lacks both methods, so when the service exists it throws an unsupported error, even before checking whether any children are active. Even without the existence check, filtering the directory with `ctx.agents.get` cannot identify external execution, and rc.2 can also have running descendants whose creator is offline. Directory traversal or looking only at direct children is not a complete active-tree release protocol.
3. The `stop`, `handOff`, in-process `resume`, and `shutdown` paths in [dsh.ts](../src/executor/dsh.ts) depend on this cleanup. A new Assignment's `launch` waits for `stopped`, but `track` swallows rejection of the stop promise; the error is recorded separately by background health and cannot be treated as a successful stop. At that initial review, `reclaim` could proceed to worktree reclamation after waiting for that tracking; if background work is still running or stopping fails, there is a risk of interference with directory use, subsequent tasks, and permission boundaries. The timeout wrapper `until` returns false rather than cancelling the underlying promise; the initial `stopSubagents` did not check that return value, so the end of the wait does not prove that the drain completed. External side effects are not rolled back by cancellation either.
4. [sessions.ts](../src/app/sessions.ts) decorates subagents on `agent/created`; `limitSubagent` searches upward for the worker via `parentSession` and parent Agents loaded in the current registry, for at most eight levels. rc.2 allows creator ancestors to be offline and cold-recovers only the target, so this chain may fail to find the worker and apply `workOnly`. This is an authorization risk that needs reproduction and closure, not a confirmed production vulnerability. Permission propagation also needs checking for reuse, recovery, deeper levels, and external backends; external backends retain their own permission systems, so their security cannot be inferred from the local Agent hook alone.
5. rc.2's tree-level communication, names, notification scope, directory version, default interrupt tool, and permission checks may all change the model experience and custom integrations; this project's work-tool allowlist and actual profile should also be reviewed. Semver, local optional TypeScript interfaces, or rc.1 mocks alone cannot prove runtime compatibility.

## Archived Implementation and Validation

On 2026-11-13 the compatibility branch was rebased onto the locally available `origin/main` snapshot `9d817fa`, at the operator's choice; the authenticated GitLab remote could not be checked without credentials, so this is not a claim of the latest remote state. The snapshot removes automatic ended-Ticket worktree and local or remote branch cleanup. The candidate preserves that removal and consumes legacy cleanup effects without deleting anything. This removes the candidate's automatic deletion race, not the risk of surviving subagents, concurrent use of a retained workspace, manual deletion, or external effects. Existing deployments may still run older cleanup behavior. The earlier risk section describes the pre-rebase implementation.

The unintegrated delegation ledger now binds each generation to an Assignment ID; the bridge refuses another Assignment, and admission rechecks the persisted binding after adapter root validation. Isolated SQLite tests verify persistence and fail closed on legacy records without the field, including closed records; no automatic migration is provided. This is a consistency check on caller-supplied identity, not authentication or an Executor recovery fence. A single Assignment can still require multiple generations.

During in-process resume, the candidate persists a stop marker before cancellation. If cancellation throws, it records the error, still attempts cleanup and processes later Tickets, and retains that marker even if cleanup or a later stop succeeds. An isolated regression verifies the marker survives reopening the test database; this does not establish that external effects or GUI activity stopped.

The compatibility branch now rechecks the worker's idle state and Session sequence while joining background work. It records outstanding stops in the database and blocks subsequent executor launches and deliveries when a stop fails or cannot be confirmed. When a subagent service is present but lacks the rc.1 reusable-release methods, those executor operations are refused; **this intentionally makes rc.2 unavailable for automated worker execution rather than claiming compatibility**. rc.1 cleanup now passes catalogued external child IDs and child IDs with local Agents to `drainChildren`, including finished external historical entries: upstream releases matching resident activations and treats nonresident IDs as no-ops. The catalog omits caller-delivered external executions and does not cover startup windows. `listDescendants` derives `activity` from local Sessions, so a running external execution can appear `inactive` and that value does not prove it ended. A failed cleanup can remove an activation from the internal resident map, so a later no-op drain cannot prove that earlier cleanup succeeded. Malformed, duplicate, or unreadable stop records are also treated as quarantined; a stop already in progress does not clear a malformed record. A Ticket with a failed stop can remain quarantined indefinitely; no automatic or operator-facing release mechanism is implemented.

The worker ancestry check now reads offline ancestor headers through session persistence. A missing or unreadable ancestry does not establish that the Agent is unrelated: unresolved agents remain unrestricted, and external backends retain their own permissions. Legacy links without an origin are treated conservatively as potential worker ancestry. The quiet wait rechecks the worker sequence and its shell jobs, but admission of a new subagent or job is not atomic with the final check; a parked inbox can also exist with an unchanged sequence. The quarantine only fences this executor's paths; direct GUI actions and work already admitted before the check are outside it. The selected mainline no longer automatically reclaims ended Ticket worktrees or branches; legacy cleanup effects are no-ops. Manual or external deletion and Git operations are outside this guard, and already-started work is not revoked. An executor stop timeout does not cancel its underlying operation. The candidate now revokes stop leases and checks them and the Agent identity after asynchronous catalog reads and drains before initiating later side effects, preventing an old cleanup from going on to cancel the Agent. A drain, notification, or external side effect already started cannot be undone by that lease. The full Runtime now starts executor worker quarantine and stopping before waiting for the main Session and other activity; a main Session cancellation error no longer skips worker cleanup. If a quarantine marker cannot be persisted, the candidate skips cancellation of that worker and reports failure while continuing with other workers, so an operator must investigate it. Waiting for the main Session and effects still has no overall deadline. The candidate's HTTP-requested shutdown now invokes the exit hook with a nonzero code when stopping fails, but an exit code cannot prove that GUI activity or external effects have settled. After a failure or timeout, do not clear a marker or reclaim a workspace without an independent operator investigation and an explicit recovery design.

On 2026-11-13, isolated tests used the actual rc.1 and rc.2 subagent runtimes with an in-memory parent and mock external provider. Both versions exercised this project's `untilQuiet`; rc.2 rejected `stopSubagents` without the removed API, and the initial rc.1 implementation conservatively rejected an external catalog entry with no local Agent while that child was still running. It was subsequently changed to pass catalog IDs to `drainChildren` based on upstream source inspection. A later isolated fixture using the actual rc.1 runtime and a mock external provider verified that a running external execution is aborted and its disposal awaited, a historical catalog ID can be passed again, and a disposal error propagates. It did not cover real external processes, persistence, or startup races. The rc.2 test also verified that upstream `drainDescendants` closes that exact root while leaving another root usable. The original isolated fixtures were temporary. Separate opt-in rc.1 and rc.2 contracts under `contracts/subagent/` now have independently locked dependencies; they are installed and run separately, not by the default suite. Both contracts instantiate their respective pinned public runtime and verify drain and deregistration of a real AgentRegistry handle with an in-memory SessionStore and mock external provider; other contract cases still use in-memory substitutes. These tests did not run a real external process, a model, the full production profile, or cross-process recovery; they do not establish full compatibility or deployment readiness.

## Root Handles, Inbox, and Admission Barriers

The rc.2 [`AgentRegistry.create/resume`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.2/packages/core/agent/src/index.ts) returns an `AgentHandle` only its owner can dispose, while `get` returns a bare Agent. [`SessionController` creation and resume](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.2/packages/api/session-controller/src/agent.ts) takes `.agent` without exposing the handle to this project. The current [sessions.ts](../src/app/sessions.ts) uses that controller and cannot recover a disposable handle from its Agent. Owning handles directly would require coordinating ownership from the first creation or resume, preventing the controller or GUI from resuming first, and restoring the preset, model, and tool restrictions.

For an already-ready root, upstream [`initializeAgent` teardown](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.2/packages/core/agent-loop/src/index.ts) uses `keepInbox: !ready`, clearing pending inbox entries and persisting their deletion. An earlier cancellation with `keepInbox: true` does not change the subsequent disposal. Resuming the same ID reloads the persisted Session and history into a new Agent; it does not guarantee those pending inputs survive or that claimed messages and external effects execute exactly once. Safe migration needs an upstream disposal contract that retains the inbox, or a crash-recoverable, deduplicated durable handoff after all admission paths are fenced; existing disposal cannot simply be called lossless.

GUI [`prompt` and `updateQueue`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.2/packages/api/session-controller/src/commands.ts), and [`follow`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.2/packages/api/session-controller/src/index.ts), can deliver to or resume an Agent. Executor and tool restrictions alone do not fence these paths or already-in-flight deliveries. [`remoteAccess` policies](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.2/packages/api/remote-access/src/index.ts) always allow the owner and cannot fence the owner's GUI. A complete design needs a shared lifecycle barrier covering the owner, final enqueue, and every resume path, with in-flight operations verified; no equivalent public extension point has been identified. In particular, although `agent/created` listeners can be awaited, upstream has already entered the Agent into the registry, so another request can obtain it while a listener waits. `agent/inbox/spliced` is an after-commit notification and `agent/pre-step` only controls execution; a message has already been claimed before `agent/pre-step` and rejection does not automatically requeue it. New input can still enter the inbox during `runMaintenance`. None is a pre-enqueue barrier across all entrances. `drainDescendants` does close subagent admission for that exact root and handles child startups already in flight, but it does not cover ordinary root Session delivery or direct Agent input; child completion notices can still be injected into the root during cleanup.

## Local Delegation Root Design Draft

The selected direction is to explore a delegation architecture inside this project, rather than assuming upstream will restore the old API. The proposed design keeps the existing worker Session, GUI, inbox, and history, while this project exclusively owns a separate delegation root handle. At the end of a delegation generation it drains that exact root with `drainDescendants`, confirms success, and disposes it; subsequent delegation uses a new root. **This is not a supported runtime mode.** Only an unintegrated version protocol adapter and an in-memory generation primitive for admission and release of a supplied handle are implemented; the adapter requires an explicit protocol version and checks capabilities, and is contract-tested against both real runtimes with in-memory substitutes. Integration still needs a trusted version source; method shape alone does not prove an implementation's version. A separate experimental per-Ticket generation ledger persists states and refuses automatic reopening of unconfirmed generations; an experimental wrapper now binds a supplied handle to the ledger generation, sealing local admission and attempting to mark it unconfirmed on a start failure, and committing closing before cleanup. It attempts cleanup even after a ledger write failure or an unconfirmed admission, without clearing quarantine. After an admission-wait timeout it starts a best-effort tree drain and disposes late activations individually; these background attempts do not delay the timeout return or prove that descendants have stopped. It is not connected to the Executor or startup recovery and does not provide cross-process leases. An experimental factory now persists a reservation before asking the registry to create a handle and retains quarantine when creation is unconfirmed. Separate contracts verify real registry handle creation and disposal on both versions, but persistent Session recovery and GUI admission are not verified. The factory relies on the caller to provide trusted setup and directory restrictions; the tool and message bridges remain unimplemented. One Assignment can hand off to a person and continue multiple times, so a generation cannot simply be equated with an Assignment.

The following boundaries must be addressed before removing the rc.2 runtime refusal:

1. **Entry points and identity:** The worker preset includes native subagent tools, and the current `restrict` does not mask Agent-local tools. Isolated contracts using both real tool registries and pipelines, real Agents, and a same-name mock tool show that `restrict` does not mask a local registration, while that Agent's guard denies new calls without affecting another Agent. A call already prepared before the guard was installed still dispatches; the same holds when an installed guard permits preparation and the Ticket changes to ended before dispatch, because the pipeline does not recheck the guard. Therefore the guard cannot revoke admitted work, and this project's dynamic `workOnly` Ticket check is not an atomic barrier against tool side effects. A separate pinned-version isolated contract in `contracts/native-tools/` loads the real `tool-subagent` and `tool-subagent-control`, real tool pipelines and Agents, with a counting substitute for the subagent backend. It verifies that an unguarded native delegation reaches that substitute, new calls to four native delegation/control tools are denied by the guard, and a prepared native delegation can still reach the substitute after the guard changes. A further contract combines the real tools with the corresponding `SubagentRuntime`, real Agent, in-memory Session, and a controlled external provider: a tool call prepared before the guard changes creates a second activation, tree drain aborts both and waits for provider disposal, and a later native call is refused. The provider is still an in-memory substitute; no real external process or model is started, and GUI, the complete profile, and every executor remain unverified; all native worker entry points, including old Sessions and GUI-driven turns, and in-flight calls still need coordination. Every bridge call must bind and authorize the exact worker, Ticket, generation, and permissions through trusted state; changing an Agent argument to the root is not sufficient. A separate root is not a worker Session and its descendants have no worker ancestor, so the existing ancestry classification does not automatically apply Ticket restrictions; trusted ownership and permission propagation still need verification. An experimental bridge admission primitive binds a trusted caller's worker, Ticket, Assignment, provider, and directory, then synchronously checks Session identity, running Assignment, stop markers, and host closure at invocation, after generation admission is registered, and after the protocol adapter's root check but before invoking upstream start. It rejects recursive admissions and asynchronous final checks; a final-check refusal conservatively quarantines the generation even when the provider did not start. It is not registered as a tool and does not close native tool entry points. Isolated contracts combine the bridge, real AgentRegistry, and both real subagent runtimes with in-memory Ticket/ledger substitutes and a controlled external provider: they check caller and stop-marker rejection, await provider cleanup, and create and close two distinct roots for the same worker. Extended contracts use a real SQLite Store, generation ledger, and receipt journal in an independent temporary working directory; after closing and reopening the database they verify both generations' receipts and that `creating`, `active`, `closing`, and `unconfirmed` prevent a new generation. The test constructs those states directly. A separate isolated subprocess contract terminates only the child created by its test parent while each real runtime has an unsettled in-memory provider result; after reopening the independent database, the generation remains `active`, its receipt is absent, and a new generation is refused. Another contract lets the in-memory provider return a completed result, artificially pauses inside the capture callback before committing its receipt, and terminates the child. Both versions reopen without that receipt and continue to refuse a new generation, demonstrating potential loss in this artificially widened window. This does not establish the natural window's duration, result replay, or that external side effects stopped. Sessions and the provider remain in-memory fixtures; this is not a production recovery exercise, and message consumption is not verified. Bridge close synchronously seals admission, shares one close Promise, and waits for already registered generation admissions; isolated tests cover reentrant close during worker lookup and root validation. It still does not share a gate with Executor stop markers, so other synchronous reentrancy or another process can change state after a check. An absolute path and identifier validation are not authorization or filesystem isolation. The experimental ledger and receipt journal consistently reject empty, oversized, or malformed Unicode Ticket identifiers, but identifier validation is not authorization.
2. **Tool protocol:** rc.1 addresses children by ID; rc.2 uses tree-local names and different `list_agents`, `send_message`, and `interrupt_agent` parameters. The bridge must define the model-visible protocol and validate cross-tree and cross-Ticket addresses. Interrupt acceptance is not completion, and catalog `inactive` does not prove an external execution stopped.
3. **Results and notifications:** The separate root becomes the direct creator, so subagent results and messages reach that root, not the worker. A recoverable durable message bridge needs deduplication and ordering contracts for a stopped root, human handoff, cleanup failure, and crashes. Lifecycle events are observations, not substitutes for reliable delivery or verified cleanup. An experimental receipt journal can persist immutable results by Ticket, generation, and child and reject conflicts. The tracked wrapper requires a result capture callback and waits for it before normally disposing the root. An optional journal adapter checks a cumulative escaped UTF-8 byte budget before constructing the complete JSON snapshot and encoding it, rejects results it cannot represent losslessly, and records rejected Promises without the original error. This is not a sandbox for malicious in-process code or proxies. These components are composed only in isolated tests; they are not connected to the Executor, delivery, or consumption acknowledgement. It admits new records only for the current unclosed generation and rejects previously unrecorded late results from older generations. No upstream result replay interface has been verified for a crash before the project durably captures a caller result; a message flush confirms durable acceptance, not worker consumption. Generation closure now checks cleanup of directly held activations, but that does not prove unheld descendants or external side effects have stopped.
4. **Resources and permissions:** Own the public `AgentHandle` from root creation, enforce permissions and a working directory no broader than the Ticket, and prevent descendant bypass. Root provenance, GUI presentation, and human access also need design. Startup, stop, timeout, cleanup failure, and recovery must preserve durable quarantine.
5. **Compatibility acceptance:** Exercise both real rc.1 and rc.2 with creation, messages, descendants, external providers, repeated handoffs within an Assignment, GUI access, process recovery, and inboxes. Validate user-visible behavior changes in an independent non-production environment. The current wait, stop, and mock-external contracts do not prove these guarantees.

## Possible Migration Directions (All Require Design and Validation)

- **Defer upgrading / explicitly restrict the runtime:** Keep the known rc.1 combination until validation in an isolated candidate environment; consider tightening engines/dependencies or runtime capability checks. This is risk control only and does not mean the current release or production state has been verified.
- **Request upstream scoped release for reusable roots:** Seek an explicit Assignment-level cleanup/admission barrier that can be awaited and covers starting, local, and external descendants; reopen it after completion or provide generation semantics. Do not simulate this by calling a private manager, manually enumerating and interrupting instances one by one, or assuming that a drain timeout means success.
- **Redefine the worker handle lifecycle:** Explore stopping all new input at Assignment end, running `drainDescendants` on the root and confirming successful cleanup, then releasing the original root's Agent handle. A later Assignment would rematerialize a new exact root from the persisted Session and restore tool restrictions and the inbox. This must first prove that this project's Sessions ownership, handle release/recreation APIs, event and input ordering, cold recovery, and permissions can safely support it; calling drain on the same root and then continuing to use it is not enough. Human handoff, shutdown, failure, and retry also need separate designs.
- **Continue investigating alternative isolation models:** For example, use a separate root per Assignment with explicit cross-Assignment context recovery, or manage independently owned activations through a controlled adapter. This changes Session continuity and caller ownership and cannot be assumed to be low-cost. Any solution should block restart and worktree reclamation on failure, distinguish timeout, unconfirmed, success, and partial failure, and provide an operator-visible recovery path.

Recommended acceptance coverage: a real rc.1/rc.2 dependency matrix; direct children, grandchildren, external execution, early exit of intermediate creators, and cold recovery; a running/idle parent, parked inbox, notifications, and Session sequence number races; drain during creation, concurrent new input, cancellation, timeout, and release failure; delegation by a new Assignment after the previous one ends, with permissions still constrained by the Ticket; no worktree reclamation while background stop is unconfirmed; inbox restart, duplicate messages, and external side effects; shared storage across versions, rollback, and failure recovery. Tests should run with an independent non-production profile, DSH home, state database, port, credentials, and test repository, without enabling production Feishu; a worktree alone does not isolate processes or credentials.

## Unresolved Questions

1. Does upstream plan a public release API covering the entire tree without permanently closing the root, or a reopenable generation? If not, what is the formal host contract for rebuilding a root?
2. Can this project release and safely rebuild an Agent from the same Session while preserving claimed/unclaimed input, restrictions, event ordering, and history? How can each failure point be recovered without repeating external operations?
3. How can durable, unforgeable root ownership establish worker Ticket authorization, especially with offline ancestors, deep trees, cross-backend and recovery paths? How can external execution permissions and stopping be verified?
4. What are the service-level objectives, alerts, isolation, and manual procedures for waiting, parked inboxes, stop failures, and timeouts? How can worktree reclamation establish a reliable barrier against these states?
5. How can compatibility and rollback be validated for existing historical Sessions/directories and new writes in rc.2? How can all processes sharing storage coordinate upgrades and avoid concurrent ownership? The official requirement to upgrade together does not provide cross-process leases.
