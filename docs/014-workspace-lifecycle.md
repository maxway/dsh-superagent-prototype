# 014 Safe workspace lifecycle

Status: **implementation in progress**. This checkout replaces destructive cleanup with read-only per-Ticket observations and stores the latest report; it does not yet implement automatic resource deletion, retention, ownership adoption or automatic restoration. The selected policy is restricted automatic cleanup of verified Superagent-owned local resources and conditional deletion of verified merged Superagent-owned remote branches. This is not a claim about the deployed version and does not authorize operations on production. See [session retention](010-session-retention.md) and [worker handoff](012-worker-handoff.md).

## Existing behavior and risk

The previous Executor implementation enqueued a cleanup effect after a Ticket ended and again for ended Tickets at host startup; a deployed version may still do so. It waits for known stopped work, checks the worker Session and Ticket, then checks the expected branch, linked-worktree shape, normal Git status and commit reachability from local remote-tracking refs or the Ticket's fetched ref. It can force-remove the worktree, delete the local branch and fetched ref, and, for merged own pull requests, try to delete a remote branch after comparing its tip with local HEAD. These are properties of the previous implementation, not proof of what is deployed. Checks and deletion are not a transaction: normal status omits ignored files, remote-tracking refs may be stale, `--force` may remove data Git otherwise protects, and a separate remote read followed by ordinary delete is not compare-and-swap (CAS). A fetched ref is local, not proof of remote durability. Neither a clean result nor an ended Ticket proves no process or person uses the directory. Existing in-process coordination does not fence other processes, hosts or direct Session use.

A previous launch implementation prepared a missing directory and treated an existing directory as prepared without establishing historical identity. A previously deployed recovery did not enforce these checks. The candidate recovery checks described below do not establish an OS security boundary: a worktree is source isolation, not process or credential isolation.

## Ownership and inventory

For this deployment the operator states that other users and systems do not operate Ticket workspace directories or the exact Superagent-owned per-Ticket branches and refs. Other worktrees, branches and the common Git repository are shared and may change concurrently. This is an operational trust assumption, not an OS-enforced fence, and never establishes ownership by a name alone. If the assumption cannot be maintained, automated deletion must not run.

Treat the Ticket, Assignment and Session as distinct from resources: worktree directory and Git administrative entry; common repository and objects; local branch and Ticket fetch ref; remote repository and branch; untracked and ignored files, submodules and nested repositories; external jobs, processes and their outputs; and persistent application state and external change requests. They have different owners and lifetimes. Ending a Ticket, handoff, merging a change request, or a directory name matching a convention does not transfer or extinguish ownership. The stable checkout, other task worktrees, shared Git objects, unrelated refs, and another service's state are never scratch space.

When `executor.managedRepository` is configured before a new Ticket is accepted, the candidate records a generation, repository and expected paths and refs, checks their absence before prepare, and attempts to verify the linked worktree, refs, object IDs and filesystem identities afterward. Failed or incomplete checks remain unknown; older Tickets are not adopted. This evidence is partial and does not authorize deletion. The local-ref CAS and journal and remote conditional-delete helpers are isolated building blocks, not connected to automatic cleanup; the local helper requires an independently enforced exclusive lifecycle and a trusted Git runner. A retained Git ref protects an object, not the workspace or reflog history, and its retention and release policy is not yet implemented.

A complete managed-resource record must additionally bind deployment/state identity, Assignment, host identity, source/provider and remote repository identity, and the prepare configuration used at creation. Record whether the resource is managed, externally supplied, shared, or unknown. Resolve symlinks, junctions, case and cross-platform paths carefully; a path string or branch prefix alone is not proof. Record creation and partial-failure stages before and after effects, without storing credentials. Configuration changes do not retroactively change an existing resource's owner.

## Near-term: read-only reconciliation

The candidate implementation handles both previously queued cleanup effects and startup re-enqueue as read-only inventory; it does not delete worktrees, branches, refs or remote branches. For an inventoried Ticket it stores one latest observation, with observation time and Ticket end time, in the state database and exposes it in the Ticket detail API and panel. If a Ticket ends without an unfinished Assignment, inventory is not queued until the next startup; failed or paused inventory may also leave no current report. It reports the directory, exact local branch and Ticket ref where the repository can be inspected, and whether Git reports ignored entries. Tracked and untracked changes remain unknown: automatic inventory does not run `git status`, which can execute repository-defined clean filters. Remote state, ownership and missing or broken repositories remain unknown. It does not scan orphan refs without a Ticket, check external processes, prove ownership or record a complete audit history. The report is a point-in-time observation, not a deletion plan or permission; it may be stale immediately. Git uses optional locks disabled and filesystem monitoring disabled; it does not fetch, prune or run prepare as part of inventory.

An operator can run `node scripts/workspace-inventory.mjs --repo <local-git-repository>` to enumerate registered worktrees, `agent/` branches and Ticket refs without a database. Optionally pass `--db <sqlite-state-file>` to associate exact Ticket IDs, directory names and branch names using a quiescent, consistent database snapshot. The tool refuses an existing WAL file but its check cannot fence a concurrent writer; never point it at a live database. For `agent/` branches it also reports configured upstreams and whether Git lists their local tracking refs, including `[gone]` when none is listed. A dangling symbolic ref may also be unlisted. This does not compute ahead/behind, may be stale, and is not proof that a remote branch is absent. Names and paths are only associations, not ownership evidence, and orphan directories without a Git registration are not discovered. It performs no deletion.

Historical worktrees and refs generally lack reliable provenance: inventory them without adopting or deleting them. A human must explicitly confirm identity, ownership, use, preservation and intended action per resource; even confirmation is not a substitute for future technical safety gates. No age, name, Ticket terminal state, merged status or absence of a database row alone authorizes cleanup. No automatic migration may infer that an orphan is disposable. Rollback must not let an older binary replay queued destructive effects or reinterpret new state: block rollback or first use a separately designed, audited compatibility procedure.

## Resume, handoff and recovery

Tickets accepted before this candidate but not yet launched, including off-peak or queued Tickets, do not have its creation claims. If their workspace or worker Session has not been created, launch fails closed and requires operator investigation rather than automatically preparing or creating it. Inventory these Tickets before upgrading; no automatic migration or operator recovery procedure is implemented.

Before resuming an existing Ticket, an operator must verify the original worktree, branch, uncommitted and ignored work, Git common directory, Session working directory and external activity. The candidate records a preparation claim before running prepare, refuses to recreate a missing historical directory, and checks the branch and Git common-directory path captured for newly prepared Git workspaces. When the filesystem supplies nonzero identities, it records the new workspace directory's device and inode and, for Git checkouts, the canonical common and worktree Git directories and their identities. It refuses later mismatches or a workspace symbolic link. These checks cannot detect every replacement, including identity reuse; historical claims and filesystems without usable identities have no such baseline. An interrupted preparation is retained for operator inspection. Existing Session creation-directory metadata is checked, and a new worker's creation timestamp is recorded when available and checked on later use. That immutable header does not prove the Session's current working directory: timestamps can collide or be copied, so they do not reliably distinguish a recreated Session with the same ID and cwd. A matching common-directory path or branch does not prove repository identity either. For a new worker the candidate rejects a Session already visible when its create workflow starts and rejects a create response naming another Session. The controller may still reuse a blank Session that appears during creation, so these checks do not establish exclusive creation. A durable per-Session creation marker would need a confirmed persistence barrier and fail-closed recovery across the Session and Ticket stores; no such marker is implemented yet. Legacy Tickets with existing directories may still resume after the available checks; they have no trustworthy baseline and are not automatically adopted or proven safe. Restore only from verified original resources or a known-good backup with explicit operator coordination, then reconcile external changes. Preserve old sessions, reports and source records even when recovery is impossible, and report missing data honestly.

Handoff is not resource transfer. The existing capability-tier handoff is narrower than the proposed protocol in [012](012-worker-handoff.md): do not assume it stopped every process or assigned ownership of the old worktree, branch or remote change request. The successor gets no implicit authority to modify or delete those resources. Any future transfer requires explicit authorization, a durable owner/generation change, verified quiescence and a consistent manifest; ambiguous or ongoing external effects require human handling.

## Future destructive lifecycle — prerequisites, not an implementation plan

Deletion is a separate, opt-in feature requiring explicit product and operator approval, independent resource-level policy, audit, dry-run, retention and recovery design. Until then no automatic worktree, branch, ref, Session, database or remote deletion is promised. A Ticket may be resumed before its queued launch waits for cleanup, and direct Session input bypasses that wait. Rechecking idle immediately before an asynchronous Git command is not a fence. A complete protocol needs a durable claim coordinated with Ticket state transitions and a host-enforced gate covering every Session entry point, kept until the Git process exits and its outcome is recorded; unknown crash outcomes require reconciliation, not lease expiry. A proposed deletion protocol must at least:

1. Acquire a durable exclusive lifecycle claim fenced by resource generation, and serialize launch, resume, handoff, creation and cleanup across instances. Re-read identity and state immediately before each irreversible effect. A lease alone does not fence an uncooperative external process; lack of provable exclusivity means retain and escalate.
2. Confirm owner, authorization and exact repository, worktree and ref identity; no active or pending Assignment, Session turn, subagent, managed job, handoff, input or recovery claim may need it. Inventory independently launched processes, open files and external users where possible. A stopped tracked job, PID absence or an idle Session does not prove there are no detached processes; when evidence is incomplete, require human coordination rather than kill processes broadly.
3. Inventory tracked, untracked **and ignored** files, nested repositories, submodules, symlinks and generated artifacts, including secrets and irreplaceable local data. Ignored does not mean disposable; no force removal or `git clean` based solely on normal status. Preserve or explicitly authorize each class, and block on unknowns or races.
4. Establish independent durable recovery before removing a local ref or worktree. A protected ref should preserve the exact object ID under a dedicated managed namespace, created with an expected-old-value check, tied to a durable ownership record and retained until its explicit release policy is satisfied. Protecting commits does not preserve uncommitted, untracked or ignored files, submodule repositories, external artifacts or remote availability; it is not a complete backup. Git GC, repacking and shared object stores must respect the protection. Never overwrite or delete an unrelated ref.
5. Treat local and remote deletion as separate operations. Confirm the remote repository identity, branch ownership and actual expected remote object ID; delete only via a server-enforced conditional update (for Git, a deletion with an explicit expected-OID `--force-with-lease` where supported). A preflight `ls-remote` followed by ordinary delete is not CAS. A changed, absent, inaccessible or uncertain remote result requires re-observation and explicit resolution; do not blindly retry. Protected branches or providers that cannot enforce the condition remain untouched.
6. Persist intent, expected identities and OIDs, authorization, per-step outcomes and a durable audit before/after each effect. Model partial completion explicitly: remote delete, local worktree removal, ref removal and state update cannot be one transaction. On crash, inspect actual state and reconcile idempotently; unknown external outcomes require human review, never infer success from an attempted command. Do not mark a multi-step operation complete until every required result is verified.

Remote ownership must be established separately from source observations: an `own` follow, matching branch suffix or observed source OID does not prove exclusive ownership or the OID merged by the provider. A future protocol needs durable evidence of controlled creation of the exact source ref in the exact provider repository, authoritative merge-time source and target identities, and independent validation of the target result. Conditional deletion protects only the expected OID; it does not prevent an ABA recreation or prove repository identity.

A trash rename is not universally atomic across filesystems and may break Git worktree administrative paths; it is not a generic undo mechanism. Backup consistency, retention of protected refs and secrets, disk capacity, garbage collection, and restore testing need their own design. Age/size thresholds never override ownership, process or data safety. Session deletion also requires a supported DSH persistence API and coordination with its locks and workspace registry; manual file deletion is not a safe substitute.

## Validation before any rollout

Use isolated test repositories, homes, state, credentials and processes, never production data. Cover ignored-only data, submodules and nested repositories; symlink/junction and case aliases; unknown legacy worktrees; stale tracking refs; remote branch movement between read and delete; concurrent resume, handoff and direct Session use; detached external processes; and changed configuration or Git host. Inject crashes before and after every durable write and external effect, including lost remote responses and partial local removal; verify fail-closed behavior, idempotence, audit and rollback compatibility. Confirm queued legacy effects cannot delete after upgrade, read-only scans do not modify resources, and all destructive actions remain disabled by default. Deployment and production observation require a separate explicit request.
