# Agent instructions

## Pull request language

Write pull request titles and descriptions in Simplified Chinese. Keep subsequent PR description updates and PR discussion replies in Simplified Chinese as well, unless the user explicitly requests another language. Preserve code identifiers, commands, paths, and quoted technical terms as appropriate; translate the surrounding explanations.

## Self-hosted development: protect the running service

This repository is developed by dsh-superagent itself. The goal is to deliver new features regularly without letting a failed development build, test, or candidate deployment stop or corrupt the superagent that is doing the work. Development, candidate validation, and production release are separate operations. A worktree is source isolation, not a process, credential, or data isolation boundary.

The intended stable checkout is `F:\code\dsh-superagent-prototype`, also visible in WSL Ubuntu as `/mnt/f/code/dsh-superagent-prototype`. It is the stable source checkout and Git source for task worktrees, not a scratch checkout; the 2026-11-14 local runtime cutover uses a separate runtime directory. One main clone plus one temporary worktree per concurrent task is the preferred steady state; do not create a permanent extra clone unless cross-platform Git, dependency isolation, or recovery needs justify it. Ticket worktrees are still required for the work they isolate.

Recheck live process, profile, bundle link, state, worktrees and changes; dated service-isolation and removed-ticket history is in [deployment](docs/006-deployment.md#production-host-for-this-checkout).

### Development and candidate tests

- Work in the assigned task worktree; verify its Git common directory and branch before editing. Never treat the stable checkout, production state directory, or another task's worktree as scratch space. Preserve existing uncommitted work.
- The current candidate does not automatically delete ended Tickets' worktrees or local or remote branches. Existing deployments may still run older cleanup behavior until upgraded; verify the deployed version before relying on retention.
- The rc.3 compatibility candidate blocks known native subagent tools for recognized managed workers and descendants, but is not an isolation boundary. On rc.2/rc.3, catalogued history or observed tree work makes cleanup unconfirmed and preserves the existing persistent Ticket fence; there is no automatic release. Empty catalogs and a false wait do not prove no work remains. On in-process shutdown failure retain the database and state lock, report `shutdown_failed` in runtime health, and investigate the original process and remaining work before recovery; Windows stop and restart fail without forcing a kill or starting a replacement. Crashes before intent recording, direct GUI actions and external or unrecognized work remain outside the safeguard; see [compatibility](docs/014-dsh-rc3-compatibility.md). This candidate is not a production deployment.
- Do not run install, build, clean, checkout, reset, pull, or other mutations in the stable checkout as part of development or testing. A linked bundle can read files from that checkout; changing it while the service runs is not a safe deployment mechanism.
- Use one non-production server for development and candidate validation, separate from production in profile, DSH home, state and database, control files, logs, port, working directory, credentials and sources. Do not consume or mutate production tickets, accounts, notifications or external repositories; use mocks or a dedicated test repository.
- Deployment and lifecycle tests must explicitly select a temporary service home, checkout, and fake executor or a test-owned endpoint held for the operation; do not rely on inherited `DSH_HOME`, default home, a fallback checkout, or a port released before use. Git-mutating tests must use explicitly created temporary repositories and clear inherited Git location and configuration overrides. A task worktree, separate runtime directory, and isolated environment do not prevent access to production loopback ports or processes. Verify the target before any real lifecycle operation.
- Only production may enable Feishu. The non-production server must have Feishu disabled and no production bot credentials or CLI configuration. Do not copy production profiles or databases into it; a disabled Source alone does not prevent setup from checking a saved bot configuration.
- Before resuming an existing ticket, verify its original worktree, branch, uncommitted work and session working directory. A missing directory is not evidence that it is safe to recreate from the current prepare command; stop and ask an operator to recover it. The candidate's filesystem identities and Session creation timestamp are partial checks, not proof of original identity or isolation; older records may lack them. The previously deployed recovery did not enforce these checks.
- The lifecycle candidate records read-only observations of ended Ticket resources and disables the old automatic destructive cleanup; this does not establish ownership or authorize deletion. Older deployed versions may still run the destructive path. See [workspace lifecycle](docs/015-workspace-lifecycle.md), recheck the deployed version, and preserve ignored files and historical unknowns.
- The service script uses a profile-specific tmux socket, passes the caller's `DSH_HOME`, `HOME`, and `PATH` to its pane, and clears `TMUX`/`TMUX_PANE` before DSH starts. Preserve this isolation: `TMUX_TMPDIR` alone does not override an inherited `TMUX`. These guardrails are not an OS security boundary; workers must not target the service socket.
- Never stop, restart, kill, or reconfigure the production process, profile, WSL distribution, host, or shared dependencies to make a test pass. Do not use broad process-kill commands such as `pkill` or `killall`, unqualified `tmux kill-server`, or `wsl --shutdown`. Test cleanup may target only explicitly created test processes and isolated sockets. Confirm the target identity before any lifecycle operation; if isolation is uncertain, stop and ask the operator. Diagnose service failures from evidence; do not add automatic restart as a substitute for identifying and fixing their cause.
- The intended production host is native Windows with a separate F: runtime directory and a dedicated DSH home. For pinned configuration, compatibility wrapper, state, legacy controls, and 2026 cutover observations, see [deployment](docs/006-deployment.md#production-host-for-this-checkout). Keep Windows and WSL dependency trees separate and preserve historical WSL state and worktrees.
- Windows WMI process creation for the service wrapper requests a hidden window; preserve that behavior when changing the out-of-Job launch path, including its Windows tests.
- The intended Watchdog observer only reads service snapshots via GET and writes local state, logs and heartbeat; it does not run a model, notify Feishu, write to the service, recover services or Tickets, poll deployment requests, or update itself. The launcher runs the installed version only. Existing production needs a separate Watchdog deployment before this applies; inspect local evidence because there is no proactive notification. Service-side enforce APIs may remain callable; see [deployment](docs/006-deployment.md#independent-watchdog-process).
- The candidate disables dangerous PID-only force killing; an existing production installation may still do it until the new Watchdog is separately deployed. Without administrator access, identify a process using PID plus creation time or the same process handle, subject to permissions; reject the operation if identity cannot be established. Never infer identity from PID alone. The observer PID lock is atomically exclusive and is not automatically cleared after an abnormal exit; manually remove a leftover lock only after confirming its observer no longer exists.

### Controlled release and rollback

- A versioned Windows runtime candidate is described in [deployment](docs/006-deployment.md#versioned-runtime-candidate-windows). It is not evidence of production installation. Build and prepare a release separately from the managed Git project; do not update an active release in place. Its candidate installed-runtime wrapper, direct Node entry and activation core take physical-home and legacy-path locks, but legacy restart/recovery controls and old versions do not honor the physical lock; migration must exclude old concurrent entries, including different home aliases. The candidate's pre-stop bundle check observes the profile's filesystem link, not the bundle actually loaded by the running service. It therefore refuses to stop any running service until trustworthy process-loaded release evidence is implemented; it is not yet an automatic upgrade path. Activation, initial installation and migration require a separate operator action. Ordinary start and legacy recovery do not currently enforce the activation journal fence; after any incomplete activation, do not start or recover until an operator has investigated the journal, process, links and state.

- The local runtime uses `F:\dsh-superagent-runtime\current` and retains its dedicated DSH home and database; see [deployment](docs/006-deployment.md#production-host-for-this-checkout). Recheck actual runtime and source provenance. A complete mechanical latest-commit runtime deployment is not installed. Installed-version service controls use the runtime configuration and run independently of the service worker. The user-level legacy deployment variables and two disabled deployment tasks were removed with operator authorization; already-running processes or WMI providers may still carry inherited values, so explicitly pass empty `DSH_SUPERAGENT_DEPLOY_REQUEST` and `DSH_SUPERAGENT_DEPLOY_COMMAND` when starting the currently installed version. An explicit deployment request authorizes its necessary stop; do not ask the user to repeat it.
- The observer does not consume deployment requests or invoke crash recovery. A queued request is not proof of deployment; an independently configured executor is required. Do not confuse installed-version recovery with latest-code deployment.
- Keep production lifecycle operations outside the server's own worker and preserve other people's work. Report failures and downtime honestly. A live SQLite file copy is not a consistent backup.

### Keep this current

When changing Windows deployment, service lifecycle, worktree preparation, runtime paths, isolation, or release procedures, update these instructions and the relevant deployment documentation in the same change. Clearly distinguish verified behavior, dated local observations, plans, and unresolved questions. Recheck the live deployment instead of trusting this snapshot.
